PET WASH 2026 – COMPLETE ONBOARDING + KYC ARCHITECTURE (COPY-PASTE SPEC)

GOAL
Build a 2026-grade onboarding and KYC system with strict separation between:
- External public users (customers)
- Loyalty members (prestige club)
- Providers (walkers, sitters, hosts)
- Staff
- Management/admin
Everything must be enforced server-side and logged for legal/audit compliance.

------------------------------------------------------------
1) ROLES AND ABSOLUTE SEGMENTATION
------------------------------------------------------------
Treat each as a separate class with separate onboarding:

A) CUSTOMER (public user)
- Can browse, book, pay
- Must complete basic profile

B) LOYALTY (prestige club member)
- Customer + loyalty benefits
- Needs extra profile fields (DOB, loyalty consent)
- Optional ID only if required for wallet/benefits

C) PROVIDER (walker/sitter/host)
- Must complete full onboarding + KYC
- Must be approved before appearing in marketplace or accepting jobs

D) STAFF
- Internal operational user
- No public self-activation
- Must request access and be approved

E) ADMIN/MANAGEMENT
- Highest privilege
- Never public signup
- Invite + approval only
- Must use MFA or passkey and step-up auth for sensitive actions

------------------------------------------------------------
3) ONBOARDING STATE MACHINE (STRICT)
------------------------------------------------------------
A) CUSTOMER FLOW
Step 1: Auth (Google/Apple/Phone/Passkey)
Step 2: Complete Profile (required)
- first_name, last_name
- verified email OR verified phone
- address (manual allowed)
- accept Terms + Privacy (versioned)
Step 3: profile_status -> active
Customer can now book and use platform.

B) LOYALTY FLOW
Precondition: customer profile is active
Extra required:
- DOB (age validation)
- loyalty terms consent
Optional:
- ID only if wallet/financial perks require it
Result: role -> loyalty (or loyalty flag), profile_status stays active

C) PROVIDER FLOW (FULL KYC + APPROVAL)
Stage 1: Basic Profile
- first_name, last_name, DOB
- phone verified, email verified
- address (manual allowed)
Stage 2: Identity (KYC docs)
- national ID/passport number
- document uploads (front/back)
- selfie upload
Stage 3: Provider Profile
- services_offered
- coverage_radius_km
- experience_years
- profile_photo (public)
- bio
Stage 4: Declarations
- insurance declaration (true/false)
- provider agreement acceptance (versioned)
Stage 5: Submit
- provider_applications.application_status -> pending_review
Stage 6: Admin review decision
- approved -> application_status approved, provider becomes active_provider
- rejected -> application_status rejected, provider blocked from marketplace

Provider must NOT be able to:
- accept jobs
- appear in marketplace
- receive payouts
until application_status = approved AND kyc_status = verified (or approved policy).

D) STAFF FLOW (NO PUBLIC STAFF CREATION)
1) Staff candidate signs in
2) Creates access_request (requested_role staff)
3) Status -> pending
4) Only management approves
5) role updated -> staff
6) staff routes enabled

E) ADMIN/MANAGEMENT FLOW (INVITE + APPROVAL ONLY)
- Do not allow public intent to create admin role
- Admin is created only via:
  - super admin creates user role, or
  - access_request approved by super admin
- Admin must use MFA or passkey
- Step-up auth required for sensitive actions:
  - KYC approvals/overrides
  - payout changes
  - refunds
  - role changes
  - deleting/locking accounts

------------------------------------------------------------
4) SERVER-SIDE ENFORCEMENT (NEVER TRUST FRONTEND)
------------------------------------------------------------
Every sensitive route must enforce:
- requireAuth (validated token/session)
- requireRole (exact role rules)
- requireProfileComplete (state machine)
- requireVerifiedContact (email or phone)
- requireKYCIfProvider
- requireMfaIfAdmin (or passkey)
- writeAuditLog on every critical action

Examples:
Booking endpoints:
- role in {customer, loyalty}
- profile_status = active
- verified contact

Provider dashboard:
- role = provider
- application_status = approved
- kyc_status = verified (or policy)
- else redirect to provider onboarding

Admin routes:
- role in {admin, management, super_admin}
- MFA/passkey required
- step-up required for high-risk actions

------------------------------------------------------------
5) PASSKEYS / BIOMETRIC (2026 STANDARD)
------------------------------------------------------------
Use WebAuthn (passkeys):
- Offer "Secure your account with Passkey" after first login
- Store credential public key + metadata
- Support passkey login
- Use step-up auth (passkey re-prompt) for sensitive actions

On iPhone/iPad:
- passkey uses Face ID/Touch ID automatically

------------------------------------------------------------
6) PHONE INPUT (GLOBAL, FLAGS, ALLOWLIST, E.164 ONLY)
------------------------------------------------------------
One shared PhoneInput component everywhere:
UI requirement:
- flag on left
- country code
- then phone number
Default:
- Israel (+972) but user can choose any allowed country

Rules:
- allowlist countries you approve (Israel, USA, Australia, UK, France, Germany, etc.)
- always output E.164 to backend (example +61419773360)
- backend validates E.164 strictly:
  - must start with "+"
  - must match country calling code patterns

Never hardcode Israel only. Never block +61 etc.

------------------------------------------------------------
7) ADDRESS AUTOCOMPLETE (FAIL-SAFE)
------------------------------------------------------------
Google Places is optional enhancement.
Manual address must always work.
Store both:
- raw address_text
- structured pieces if available (city, postal, lat/lng)

If Google fails:
- show "suggestions unavailable" but allow manual entry
- never block submission

Also log:
- places_error_code
- trace_id
to diagnose production failures.

------------------------------------------------------------
8) LEGAL AND AUDIT COMPLIANCE (ISRAEL AND GLOBAL)
------------------------------------------------------------
Record these for every user action:
- Terms version accepted + timestamp
- Privacy version accepted + timestamp
- IP + user agent
- locale
- trace_id

For provider onboarding:
- KYC submission timestamp
- reviewer identity
- approval decision timestamp
- reason for rejection
- immutable audit trail for every approval action
