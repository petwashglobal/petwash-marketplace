CORE PRINCIPLE
Location is not just a display field.
Location is a core business input that must:
1. help the user enter address easily
2. store structured address + coordinates correctly
3. power nearest-provider matching and ranking
4. support fraud prevention and data integrity
5. work reliably on iPhone, Android, desktop, and after browser / firmware updates

==================================================
1. ADDRESS / LOCATION INPUT - REQUIRED PLATFORM RULE
==================================================

Every address-like field across all platforms must use the same principle:
- כתובת
- מיקום
- Location
- Search location
- Provider location
- Booking address

Required flow:
User types -> Google Places Autocomplete suggestions appear -> user selects -> UI shows human-readable address -> system stores structured location data separately behind the scenes

The user must always see a readable address.
The user must never see:
- raw coordinates
- placeId
- technical objects
- internal JSON

Correct display example:
"עוזי חיטמן 8 ראשון לציון ישראל"

Wrong display example:
"-37.8857, 145.0202"

Correct frontend logic:
input.value = place.formatted_address

const locationData = {
  formattedAddress: place.formatted_address,
  lat: place.geometry.location.lat(),
  lng: place.geometry.location.lng(),
  placeId: place.place_id
}

Critical rule:
Display value and stored value must be separate.
Never overwrite the visible input with lat/lng.

==================================================
2. GPS BUTTON RULE - CRITICAL
==================================================

The GPS / current-location button must never write coordinates into the visible field.

NEVER:
input.value = `${lat}, ${lng}`

ALWAYS:
input.value = "מיקום נוכחי"
or
input.value = "Current location"

The system should still store internally:
- lat
- lng
- possible reverse-geocoded formatted address
- street
- city
- postal code
- country

If reverse geocode fails:
- do not dump coordinates into the visible field
- show "מיקום נוכחי" / "Current location"
- keep internal coordinates
- continue search / matching from stored coordinates

Confirmed root cause that existed:
The coordinate leak was caused by GPS fallback behavior, not by standard Google suggestion selection.

Confirmed fix:
The GPS fallback now avoids showing raw coordinates in the input.

10. HAVERSINE FORMULA REFERENCE
==================================================

function haversineKm(lat1, lon1, lat2, lon2) {
  const R = 6371;
  const dLat = (lat2 - lat1) * Math.PI / 180;
  const dLon = (lon2 - lon1) * Math.PI / 180;

  const a =
    Math.sin(dLat / 2) ** 2 +
    Math.cos(lat1 * Math.PI / 180) *
    Math.cos(lat2 * Math.PI / 180) *
    Math.sin(dLon / 2) ** 2;

  return 2 * R * Math.asin(Math.sqrt(a));
}

==================================================

This is acceptable now because:

- provider volume is expected to be in the hundreds / low thousands initially

15. SECURITY, FRAUD, DATA INTEGRITY
==================================================

Never trust client coordinates blindly.

Validate:
- lat between -90 and 90
- lng between -180 and 180

Required protections:
- rate limiting on auth, SMS, search, session creation
- abuse detection on repeated spoofing or abnormal jumps
- logging of location-driven search behavior
- monitoring of suspicious patterns

Fraud / abuse signals to track:
- fake or malformed locations
- unrealistic location jumps
- repeated GPS button abuse
- mass search abuse
- mismatch between claimed area and repeated activity
