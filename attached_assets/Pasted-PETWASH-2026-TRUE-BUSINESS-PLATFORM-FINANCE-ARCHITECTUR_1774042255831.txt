PETWASH 2026 - TRUE BUSINESS / PLATFORM / FINANCE ARCHITECTURE

1. WHAT THE BUSINESS REALLY IS

PetWash is one consumer membership and wallet platform with multiple divisions:

A. K9000 stations
B. Walk My Pet
C. Pet Sitters / Boarding
D. PetWash Academy
E. Future divisions

So the platform is:

- one user identity
- one wallet
- one ledger
- many redemption channels
- many operational products

K9000 is only one redemption channel.
It is NOT the loyalty system.

2. SOURCE OF TRUTH

The real financial source of truth must be:

A. wallet_accounts
Current customer balance state

B. wallet_ledger
Append-only financial truth

C. operational tables
k9000_sessions
booking_requests
academy_orders
etc

Operational tables describe what happened.
Wallet ledger describes how money moved.

That separation is mandatory.

3. CORRECT MONEY LOGIC

Wallet account:
- available_balance_cents
- pending_balance_cents
- lifetime_earned_cents
- lifetime_redeemed_cents

Ledger entry:
- entry_type
- source_type
- source_id
- division_code
- amount_cents
- balance_after_cents
- idempotency_key
- status
- metadata_json

This means every financial movement must answer:

- what kind of movement was it
- which division caused it
- which operational record caused it
- what was the balance after
- can it be safely retried

4. ENTRY TYPES

The wallet ledger should support:

- credit
- debit
- hold
- release
- refund
- expire
- adjustment

That is the full financial vocabulary.

5. SOURCE TYPES

These should be explicit and separate from entry_type:

- k9000_wash
- booking
- academy
- reward
- manual
- gift_card
- referral
- promo

Reason:
Entry type tells you HOW money moved.
Source type tells you WHY it moved.

6. DIVISION CODES

These should be explicit:

- station_k9000
- petsitter
- walkers
- academy
- gift_card
- admin
- future divisions

Reason:
This is what gives real reporting and margin analysis by business line.

7. SINGLE WALLET RULE

One customer wallet across all divisions.

Example:
User has ₪500
Uses ₪55 for K9000
Balance becomes ₪445

That ₪445 is still usable for:
- sitter
- walker
- academy
- future services

No silo balances by product.

8. FINANCIAL FLOWS BY DIVISION

A. K9000
- preview redemption
- immediate debit on activation
- no hold
- ledger entry_type = debit
- source_type = k9000_wash
- division_code = station_k9000

B. Walker / Sitter marketplace
- preview redemption
- hold on booking create
- convert hold to debit when service starts or confirms financially
- release hold on cancel / decline / timeout
- refund where needed
- division_code = walkers or petsitter
- source_type = booking

C. Academy
- usually immediate debit on order / enrollment
- refund if cancelled under policy
- division_code = academy
- source_type = academy

9. WALLET SERVICE BOUNDARY

Every division must call one service only:

WalletService

Required methods:
- getBalance(userId)
- previewRedemption(input)
- debit(input)
- hold(input)
- releaseHold(input)
- refund(input)
- getLedger(userId)

No division should write directly to wallet tables.
No direct insert into ledger from random routes.
No business logic duplicated in endpoints.

10. IDEMPOTENCY

Every financial action must carry a unique idempotency key.

Examples:
- wallet:k9000:station123:session456
- wallet:booking:hold:booking789
- wallet:booking:debit:booking789
- wallet:academy:order321

Rule:
- if key already exists, return existing result
- if not, execute once and persist

This protects against:
- retries
- webhook duplication
- double charging
- race conditions
- frontend resubmits

11. BACKEND LAYERING

Correct server layering:

A. routes
Thin controllers only
Validate request
Call service
Return result

B. WalletService
Business rules
Preview, debit, hold, release, refund

C. WalletLedger
Append-only ledger write engine

D. WalletEngine
Deduction priority and bucket logic if needed

E. reporting services
Division usage
ROI
wallet balance history
financial exports

12. FINANCIAL MATH

Preview response must always be server calculated.

Example:
division = station_k9000
subtotalCents = 5500
walletAvailableCents = 50000
walletRedeemableMaxCents = 5500
walletAppliedCents = 5500
cashDueCents = 0

For bookings:
subtotalCents = 12000
walletAvailableCents = 50000
walletRedeemableMaxCents = 6000 if 50 percent cap
walletAppliedCents = 6000
cashDueCents = 6000

Never trust frontend calculations for money.

13. REPORTING MODEL

Because division_code exists in wallet_ledger, you get:

- wallet usage by division
- revenue impact by division
- redemption cost by division
- lifetime earned vs redeemed
- margin impact per business line

Core reporting query:
SUM(debit amounts) grouped by division_code

This is essential for management.

14. FRONTEND PRODUCT MODEL

The loyalty page should not feel like a wash dashboard.

Correct page structure:

SECTION 1 - HERO
- pure white
- large premium diamond mark
- member name
- tier
- member ID
- one primary membership card

SECTION 2 - BENEFITS
Cross-division benefits:
- K9000 discounts
- sitter / walker perks
- academy perks
- priority / privilege benefits

SECTION 3 - DIVISION ACTIVITY
Separate tabs:
- K9000
- Walkers
- Sitters
- Academy
- All

Do not mix everything into one generic feed.

SECTION 4 - WALLET
- total privilege balance
- available
- pending / held
- expiring credits
- rewards earned
- bucket breakdown if relevant

Label:
- PetWash Wallet
- PetWash Privilege
- Privilege Balance

Never “wash credits”.

SECTION 5 - DIGITAL CARD
- Apple Wallet
- Google Wallet
- QR
- email card / pass

This belongs lower in hierarchy, not at the top.

15. MOBILE / UI RULES

Mandatory:
- pure white background
- larger premium logo
- remove dark dashboard styling
- remove duplicated tiles
- tighter spacing above hero
- mobile-first vertical rhythm
- floating widgets must never cover card content
- extra bottom spacing for widget stack
- chat widget collapsed by default on mobile
- lower widget z-index conflicts resolved cleanly

16. OPERATIONAL CONNECTIONS BETWEEN SERVICES

How the platform really connects:

User Identity
  ->
Membership / Privilege
  ->
Wallet Account
  ->
Wallet Ledger
  ->
Division Services

Division services:
- K9000 station activation
- marketplace booking engine
- academy checkout
- future services

Each division:
- requests preview
- asks wallet to reserve / debit / refund
- stores operational record separately
- links back through source_id

That is the correct SaaS architecture.

17. SECURITY RULES

Must enforce:
- server-side calculation only
- append-only ledger
- idempotency for all financial actions
- no route writes directly to balances
- balance cache always reconciles against ledger
- strict auth on wallet endpoints
- admin adjustment audit trail
- refund / adjustment reasons stored
- metadata_json for traceability
- division_code always stamped
- source_type always stamped

18. WHAT MUST BE REMOVED OR FIXED

These are wrong and must not remain as the dominant model:
- wash-centric naming
- wash-only balance concepts
- using operational tables as financial truth
- UI that mixes profile/dashboard/wallet into one messy block
- direct deduction logic duplicated per route
- no division tracking in ledger
- dark / cluttered prestige page
- widget overlap on mobile

19. CORRECT FINAL PRODUCT POSITIONING

PetWash Privilege is:
- the shared customer value layer
- the shared financial wallet
- the shared redemption system
- the shared cross-division identity
- the retention engine across the entire ecosystem

K9000 is one use case.
Not the system itself.
