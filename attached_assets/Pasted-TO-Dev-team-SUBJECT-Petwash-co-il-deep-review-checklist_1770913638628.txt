3) Unified “Octopus Brain” architecture (multi-platform, one ledger)
======================================================================
You want Uber-style separation by operation, but one shared brain.

Core principles
- One Identity: one user record per person.
- One Wallet: balances for egift and packages, usable across products.
- One Ledger: every financial movement is an immutable transaction event.
- One Booking engine: product-specific booking schemas, same lifecycle.

Suggested Firestore model (high level)

users/{uid}
- displayName, email, phoneE164
- roles: { client: true, provider: true, staff: true, admin: false }
- locale, createdAt

providers/{uid}
- status, servicesEnabled: { sitter: true, walker: true, driving: false, academy: false }
- kyc: { level, verifiedAt }
- payout: { method, last4, bankTokenRef }
- complianceAcceptedAt

wallets/{uid}
- availableCreditNis
- holdsNis
- updatedAt

walletEvents/{eventId} (immutable)
- uid
- type: CREDIT_PURCHASED | WASH_REDEEMED | BOOKING_CHARGED | REFUND_ISSUED | ADJUSTMENT
- source: EGIFT | PACKAGE | BOOKING | KIOSK
- product: wash | sitter | walker | driving | academy | pettrek
- amountNis (positive or negative)
- refId (eg egiftId, bookingId, kioskTxnId)
- createdAt
- metadata

egifts/{egiftId}
- uidOwner (or recipientEmail/phone)
- designStyle
- washesTotal, washesRemaining
- status: active | void | expired
- createdAt

packages/{packageId}
- uid
- type: WASH_5 | WASH_10 | VIP_MONTHLY etc
- unitsRemaining
- status
- createdAt

bookings/{bookingId}
- product
- clientUid
- providerUid
- status: requested | accepted | in_progress | completed | canceled
- pricing: { subtotal, fees, tax, total }
- payment: { method, walletAppliedNis, externalChargeId }
- createdAt

invoices/{invoiceId}
- legalInvoiceNumber
- uid
- entity (company details)
- lineItems
- totals
- issuedAt
- pdfUrl
- hashStamp (optional)

Why this matters
- Any egift or package becomes just a wallet credit or unit-based entitlement.
- Kiosk redemption records are walletEvents with source=KIOSK and refId = kioskTxnId.
- Bookings consume wallet credit or trigger card charge, always recorded in walletEvents.

5) Best-practice 2FA for iOS + Android + web (email + SMS)
======================================================================
You asked: “two way verification option for users who desire it”.
Answer: Make 2FA optional per account with “preferred method”.

Preferred approach (cleanest)
- Use Firebase Auth for primary login (email/password, Google, Apple, phone).
- Implement 2FA as a second step AFTER primary login:
  - SMS: Twilio Verify (do not generate codes yourself)
  - Email: your own OTP (or a provider like SendGrid) with hashed code storage

User settings
users/{uid}/security
- twoFactorEnabled: boolean
- methodsEnabled: { sms: true, email: true }
- preferred: sms | email | both
- phoneE164Verified: boolean
- emailVerified: boolean

Flow
1) User logs in (normal)
2) If twoFactorEnabled:
   - Start challenge
   - Verify challenge
   - Issue session flag “twoFactorPassed” for that device session (short TTL)

Device session record (server-side)
sessions/{sessionId}
- uid
- deviceId (hashed)
- twoFactorPassedAt
- expiresAt

Implementation notes
- Twilio Verify handles regional permissions and OTP lifecycle for SMS.
- Email OTP must be rate-limited, hashed, and expire quickly.

Security requirements
- OTP expiry: 5 minutes
- Max attempts: 5
- Rate limit: 3 sends per 10 minutes per uid and per IP
- Store only hash of code, never plaintext.

Minimal backend endpoints
POST /api/2fa/start
- body: { method: "sms"|"email", phoneE164?, email? }
- returns: { challengeId }

POST /api/2fa/verify
- body: { challengeId, code }
- returns: { ok: true, session2fa: true }

If you want “both”
- Start two challenges and require both to pass, OR allow either.
- Keep it simple: allow either unless user explicitly chooses “both required”.

Twilio region note
- If you SMS to +972, ensure Twilio Geo Permissions has Israel enabled.
