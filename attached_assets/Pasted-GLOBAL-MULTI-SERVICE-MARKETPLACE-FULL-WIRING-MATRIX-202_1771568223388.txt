GLOBAL MULTI-SERVICE MARKETPLACE - FULL WIRING MATRIX (2026)
Purpose: One system. Multiple services. Fintech-grade security. Legal-grade records. Zero ambiguity.
Rule: No competitor names anywhere in UI, DB, logs, emails, or copy. Use internal neutral terms only.

====================================================================
0) CORE PRINCIPLES (NON-NEGOTIABLE)
====================================================================
1. Server is the source of truth. Client cannot set role, status, approval, pricing, KYC result, payouts, or permissions.
2. Every sensitive action is auditable with traceId + actor + IP + userAgent + before/after snapshots (when allowed).
3. Consent is explicit, versioned, timestamped, and bound to userId + device + locale. No consent, no action.
4. Compliance is enforced by gates at API level, not by frontend routing.
5. Every user type has a state machine. Every state machine is enforced in DB and API.
6. Any failure must degrade gracefully:
   - Address autocomplete fails -> manual entry still works
   - OTP fails -> alternative method (email or passkey) offered
   - Payment preauth fails -> booking cannot dispatch
   - Sheets or BI sync fails -> core DB still commits

3) STATE MACHINES - EXACT RULES
====================================================================

A) Customer / Loyalty user_status
- NEW
- PROFILE_INCOMPLETE
- PROFILE_COMPLETE
- (optional) KYC_PENDING (loyalty only if KYC required)
- KYC_APPROVED (loyalty only)
- SUSPENDED

Transitions:
- login first time -> NEW
- if missing required profile fields -> PROFILE_INCOMPLETE
- submit profile -> PROFILE_COMPLETE
- if loyalty and KYC required -> KYC_PENDING
- KYC approved -> KYC_APPROVED
- fraud or policy -> SUSPENDED

B) Provider user_status
- NEW
- PROFILE_INCOMPLETE
- PROFILE_COMPLETE
- KYC_PENDING
- KYC_APPROVED
- PROVIDER_PENDING_APPROVAL
- PROVIDER_ACTIVE
- SUSPENDED

Transitions:
- provider intent selected -> onboarding_case(context=provider)
- profile complete -> PROFILE_COMPLETE
- submit KYC -> KYC_PENDING
- KYC approved -> KYC_APPROVED
- ops review -> PROVIDER_PENDING_APPROVAL -> PROVIDER_ACTIVE
- any risk -> SUSPENDED

C) Staff user_status
- NEW
- STAFF_PENDING_APPROVAL
- STAFF_ACTIVE
- SUSPENDED

Transitions:
- staff request -> STAFF_PENDING_APPROVAL
- admin approves -> STAFF_ACTIVE (and set MFA required)
- policy violation -> SUSPENDED

No direct transitions allowed from client. Only server.

4) FRONTEND INTENT-FIRST ENTRY (ONE SIGN-IN PAGE, MANY FLOWS)
====================================================================

A) Intent Cards (pre-auth)
- "Book a Service" (customer)
- "Join Premium Membership" (loyalty)
- "Apply as a Provider" (provider)
- "Request Staff Access" (staff_request)

Client stores intent locally for UX only.
Server stores intent in users.signup_intent after auth.

B) Auth Methods
- Passkey (WebAuthn) first if available
- Phone OTP with country flags + allowlist
- Email (magic link or passwordless)
- Social login (only if configured)
- Fallback to another method if blocked

C) Post Login Decider (server)
POST /api/auth/post-login { intent, deviceInfo }
Server returns:
- nextPath
- requiredActions (array)
- user_status
- role
- onboarding_case_id

D) Required Actions UI (front end)
- Complete Profile
- Verify Email (if email method)
- Enroll MFA (privileged roles)
- Submit KYC (provider, loyalty if required)
- Wait for Approval (provider and staff)
- Accept Terms and Policies (versioned)

Frontend must never guess. It renders what server returns.

8) KYC ARCHITECTURE (BANK-GRADE BEHAVIOR)
====================================================================

A) Modes
1) TTL storage mode
- store raw docs in secure storage
- strict TTL lifecycle delete (example 24h)
- store only fingerprints and results long term

2) Zero storage mode (ideal)
- upload to server
- process in memory
- generate fingerprint_hash and extracted fields minimal
- wipe buffers
- do not persist raw files
- persist only: kyc_checks, risk score, audit record, fingerprint hash

B) Checks chain (example)
- document intake validation (mime, size, type)
- OCR extraction (minimal fields)
- face detection
- liveness (challenge or passive heuristic)
- face match (embedding model preferred)
- risk scoring
- manual review queue if needed

C) KYC outcomes
- approved -> unlock provider activation
- rejected -> block and allow resubmission after cooldown
- manual_review -> hold until compliance team action

D) Security requirements
- rate limiting per user and per IP
- anomaly detection (velocity, device, geo mismatch)
- admin view logging for each document or case

10) DISPATCH AND PROVIDER EXECUTION (THE OPERATIONAL BRAIN)
====================================================================

A) Provider Presence
- provider sets availability: online|offline|busy|on_job
- presence heartbeat updates last_presence_at
- server considers stale if last_presence_at older than threshold

B) Dispatch pipeline (DB-backed, restart safe)
1) Booking confirmed with payment authorization
2) dispatch_job created
3) waves executed by poller using:
   - FOR UPDATE SKIP LOCKED
   - lease timeouts
4) Offers created with expiry
5) First accept wins:
   - atomic update with WHERE status=sent AND booking not assigned
6) On accept:
   - booking status accepted
   - provider status on_job
7) On completion:
   - capture payment or finalize ledger
   - release escrow per policy
   - generate receipt record
   - award loyalty points if eligible

C) Customer transparency
- customer sees status timeline
- if expired, customer receives notification and next-step CTA

D) Provider app execution
- provider sees:
  - offer card, countdown, accept/reject
  - route details
  - job checklist
  - completion proof capture
  - support button

- redemption writes:
