PETWASH WALLET STATUS - WALKERS / SITTERS / ACADEMY / NEXT STAGE

Hi,

Here is the clean architecture summary and the next stage, written in plain business + technical logic.

1. CURRENT STATUS - WALKERS AND PETSITTERS

Walkers and petsitters are already financially wired correctly on the backend.

What is already working:
- wallet hold on booking creation
- wallet debit from hold on provider accept
- wallet release on decline
- wallet release on cancel before debit
- wallet refund on cancel after debit
- reconciliation job scans for drift and heals accepted bookings stuck in hold_active
- ledger entries are idempotent
- division stamping exists in the wallet ledger
- reporting by division is already possible

So financially:
- Walkers = correct
- Petsitters = correct

This means the backend wallet model is no longer K9000-only.
The multi-division architecture is now real.

2. WHAT IS STILL MISSING

The remaining gap is mostly UX consistency, not backend correctness.

Today the user experience is still not perfectly aligned across divisions.

The user should always see, before confirming:
- subtotal
- wallet available
- wallet applied
- cash due

And that preview must come from the server, not from frontend math.

Target example:
Subtotal: ₪100
Wallet available: ₪300
Wallet applied: ₪50
Cash due: ₪50

This is what the customer must see clearly in:
- walkers
- petsitters
- academy

3. COMMERCIAL RULES

These rules must stay centralized in WalletService / previewRedemption:

- Walkers: wallet cap = 50% of subtotal
- Petsitters: wallet cap = 50% of subtotal
- Academy: wallet cap = 100%
- K9000: immediate debit, effectively 100% allowed based on balance and pricing

The important principle:
- server decides
- UI displays
- client never invents pricing

4. WHY THIS MATTERS

Backend is already correct.
But if the UI does not clearly show:
- what is being reserved
- what is being charged
- what returns to the wallet on decline/cancel
then users and staff will still feel the system is inconsistent.

So the next work is not "new finance".
It is "finance visibility and consistency".

5. WALKERS / PETSITTERS - WHAT TO SHOW IN UX

Booking checkout must show:
- subtotal
- wallet cap
- wallet applied
- cash due

Post-booking state must show:
- if hold exists: "₪X reserved from wallet"
- if provider declined: "wallet released"
- if provider accepted: "wallet charged"
- if refund happened: "wallet refunded"

This makes the lifecycle understandable.

6. ACADEMY

Academy backend wallet integration is now in place too:
- hold on create
- debit on confirm
- release/refund on cancel
- reconciliation support

What Academy still needs is the same UX alignment:
- preview before submit
- wallet applied line
- cash due line
- state messaging after action

So Academy is the same next-stage problem as walkers and petsitters:
backend good, UX needs alignment.

7. ARCHITECTURAL CONCLUSION

System status by layer:

- Wallet core architecture: done
- Ledger integrity: done
- Division stamping: done
- Holds / releases / debits / refunds: done
- Reconciliation: done
- Admin finance reporting: done
- Walkers backend: done
- Petsitters backend: done
- Academy backend: done
- Cross-division checkout UX alignment: next stage

8. NEXT STAGE - EXACTLY WHAT SHOULD BE BUILT NOW

NEXT STAGE: "Unified Wallet Preview + Lifecycle Messaging Layer"

Goal:
Make walkers, petsitters, and academy all feel identical and correct to the user.

Build items:

A. Shared preview contract
All division checkouts must use one server-driven preview response:
{
  subtotalCents,
  walletAvailableCents,
  walletAppliedCents,
  cashDueCents,
  pendingWalletImpactCents,
  capRule: "50_percent" | "100_percent"
}

B. Shared frontend checkout component
One reusable summary block across:
- walkers
- petsitters
- academy

It should always render:
- subtotal
- wallet applied
- cash due
- cap explanation if relevant

C. Shared lifecycle messaging
One reusable status message component:
- hold active
- released
- debited
- refunded

D. Pending wallet visibility in wallet UI
Wallet page should clearly show:
- available balance
- pending balance
- lifetime earned
- lifetime redeemed

E. Notification / confirmation wording
Customer should see exact wallet effect in booking confirmations and status updates.

9. PRACTICAL BUILD ORDER

Recommended order:
1. Academy checkout preview UI
2. Walkers / petsitters checkout preview UI
3. Shared status messaging after create / accept / decline / cancel
4. Wallet page pending balance emphasis
5. Notification wording alignment

10. ONE SENTENCE SUMMARY

Walkers and petsitters are already financially correct.
The next stage is to make walkers, petsitters, and academy visually and behaviorally consistent by using one shared wallet preview and one shared wallet lifecycle messaging layer.
