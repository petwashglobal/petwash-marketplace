FINDING 1 — GENERIC TRANSITION ENDPOINT HAS NO BOOKING OWNERSHIP CHECK
Category: Missing Permission Check | Severity: CRITICAL
File: server/routes/marketplace-bookings.ts:548–577

TypeScript

router.post('/:bookingId/transition', async (req, res) => {
  const userId = req.user?.uid || req.firebaseUser?.uid;
  if (!userId) return res.status(401).json({ error: 'Authentication required' });

  const { newStatus, role = 'customer', reason } = req.body;  // role from body — not verified

  await bookingLifecycleService.transitionStatus(
    bookingId,
    newStatus as BookingLifecycleStatus,
    userId,
    role as 'customer' | 'provider' | 'system' | 'admin',
    reason
  );
Any authenticated user who knows a bookingId can call this endpoint and drive the booking to any valid next state. There is no check that userId is the customer or provider on the booking. The role field is accepted verbatim from the request body — a customer can send role: "admin". BookingLifecycleService.transitionStatus() validates the state machine transitions but never verifies the actor's identity against the booking record.
Impact: User A can advance or cancel User B's booking. A provider can push any customer's booking to disputed. Any authenticated user can impersonate admin role in the audit log.
Fix: Before calling transitionStatus, fetch the booking and assert booking.customerId === userId || booking.providerId === userId (or admin role from Firebase claims). Derive actorRole from the booking record itself, not from the request body.

FINDING 13 — INVOICE NUMBER IS NOT SEQUENTIAL (COMPLIANCE RISK)
Category: Misleading Invoice Logic | Legal/Compliance | Severity: MEDIUM
File: server/routes/marketplace-bookings.ts:373–376

TypeScript

const datePart = now.toISOString().slice(0, 10).replace(/-/g, '');
const invoiceNumber = `INV-${datePart}-${nanoid(6).toUpperCase()}`;
// Example: INV-20260403-A7K9M2
Israeli invoice law (Heshbonim Law 5775-2015) requires invoices to be numbered sequentially and without gaps. A random nanoid(6) suffix — even prefixed with a date — does not satisfy this requirement. The Israeli Tax Authority may reject non-sequential invoice numbering during a tax audit. If two invoices happen to generate the same nanoid(6) on the same date, there is also a collision risk producing duplicate invoice numbers.
Fix: Use an auto-incrementing database sequence or a daily counter (e.g., INV-20260403-0001, INV-20260403-0002) with a unique constraint to prevent collisions.
