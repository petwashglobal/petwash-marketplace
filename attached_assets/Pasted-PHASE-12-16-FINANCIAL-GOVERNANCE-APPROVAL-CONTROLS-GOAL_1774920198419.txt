PHASE 12.16 - FINANCIAL GOVERNANCE & APPROVAL CONTROLS

GOAL
Control who is allowed to create financial risk, under what limits, and with what approval path.
This phase is not reporting. This phase is financial authority, approval discipline, and payout protection.

--------------------------------------------------
T161 - APPROVAL MATRIX (RULES AS DATA)
--------------------------------------------------

CREATE TABLE financial_approval_matrix (
  id SERIAL PRIMARY KEY,
  case_type TEXT NOT NULL,              -- 'refund', 'dispute_close', 'manual_adjustment', 'payout_release'
  action_type TEXT NOT NULL,            -- 'approve', 'hold', 'release', 'override'
  owner_scope TEXT NOT NULL,            -- 'company', 'franchise', 'station'
  owner_id TEXT NULL,                   -- null = global default, else company/franchise/station identifier
  min_amount_cents INTEGER NOT NULL DEFAULT 0,
  max_amount_cents INTEGER NULL,        -- null = no upper bound
  required_role TEXT NOT NULL,          -- 'agent', 'manager', 'franchise_owner', 'admin', 'executive'
  second_approval_role TEXT NULL,       -- null if not needed
  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMP DEFAULT NOW()
);

SEED DEFAULTS
- refund / approve / global / 0–10000 / manager / null
- refund / approve / global / 10001–50000 / franchise_owner / admin
- refund / approve / global / 50001+ / executive / admin
- payout_release / release / global / 0–100000 / franchise_owner / null
- payout_release / release / global / 100001+ / executive / admin
- dispute_close / approve / global / 0–20000 / manager / null
- dispute_close / approve / global / 20001+ / franchise_owner / admin

BUSINESS LOGIC
- this is the financial authority table
- every financial action must match one rule
- no match = action blocked
- rules are scoped:
  - global
  - company
  - franchise
  - station

--------------------------------------------------
T162 - FINANCIAL AUTHORITY CHECK ENGINE
--------------------------------------------------

BUILD
server/lib/financial-approvals.ts

FUNCTIONS
- getApprovalRule(caseType, actionType, ownerScope, ownerId, amountCents)
- canUserApproveFinancialAction(userRole, rule)
- requiresSecondApproval(rule)
- explainFinancialApproval(rule)

RULE LOGIC
- owner-specific rule beats global rule
- narrower amount range beats wider range
- inactive rules ignored
- if user role is below required_role → reject
- if rule.second_approval_role exists → mark pending second approval

OUTPUT
{
  allowed: boolean,
  requiredRole: string,
  secondApprovalRequired: boolean,
  secondApprovalRole: string | null,
  reason: string
}

--------------------------------------------------
T163 - REFUND AUTHORITY LIMITS
--------------------------------------------------

INTEGRATE INTO
- refund approval flows
- manual compensation flows
- goodwill refund flows

BUILD
Before any refund is approved:
1. resolve financial approval rule
2. compare acting user role
3. if insufficient → block with 403
4. if second approval needed:
   - create pending approval state
   - do not execute refund yet

RULE
No financial refund leaves the system without role-authorized approval.

--------------------------------------------------
T164 - PAYOUT RELEASE CONTROLS
--------------------------------------------------

BUILD
Add payout release approval gate.

APPLIES TO
- station payouts
- franchise payouts
- company-controlled payout releases

FLOW
1. payout batch generated
2. approval rule checked against total payout amount
3. if below threshold → eligible for immediate authorized release
4. if above threshold → hold and require executive or second approval

NEW FIELDS
station_settlements / payout batches layer:
- payout_hold_reason TEXT NULL
- payout_release_requested_at TIMESTAMP NULL
- payout_release_approved_at TIMESTAMP NULL
- payout_release_approved_by TEXT NULL
- second_release_approval_required BOOLEAN DEFAULT FALSE

RULE
Payout release is controlled money movement, not just status update.

--------------------------------------------------
T165 - DISPUTE RESERVE LOGIC
--------------------------------------------------

GOAL
Money attached to risky bookings must not flow out blindly.

BUILD
Reserve rules:
- if dispute is open → hold the disputed component
- if mismatch exists → hold affected payout cycle
- if refund pending → hold related payout portion until resolved

NEW LOGIC
- disputed station_settlements remain excluded from payout-ready totals
- payout calendar must show:
  - gross payable
  - held in reserve
  - released
  - blocked by dispute
  - blocked by mismatch

NO FAKE ACCOUNTING
Held money must stay visible as held, not paid.

--------------------------------------------------
T166 - FINANCIAL EXCEPTION APPROVAL LOG
--------------------------------------------------

CREATE TABLE financial_approval_log (
  id SERIAL PRIMARY KEY,
  case_type TEXT NOT NULL,
  case_ref_id TEXT NOT NULL,
  action_type TEXT NOT NULL,
  amount_cents INTEGER NOT NULL,
  owner_scope TEXT NOT NULL,
  owner_id TEXT NULL,
  requested_by_uid TEXT NULL,
  approved_by_uid TEXT NULL,
  second_approved_by_uid TEXT NULL,
  approval_rule_id INTEGER NULL REFERENCES financial_approval_matrix(id),
  status TEXT NOT NULL,                 -- 'pending', 'approved', 'rejected', 'executed'
  note TEXT NULL,
  created_at TIMESTAMP DEFAULT NOW(),
  approved_at TIMESTAMP NULL,
  executed_at TIMESTAMP NULL
);

BUSINESS LOGIC
Every high-risk financial action gets a permanent approval trace:
- who requested it
- who approved it
- which rule allowed it
- whether second approval was required
- when it actually executed

This is the audit spine.

--------------------------------------------------
T168 - FINANCIAL POLICY EXPLAINABILITY
--------------------------------------------------

For every blocked or approved action, return and store:
- which approval rule matched
- why it matched
- why the current user could or could not approve
- whether second approval is required

Example response:
{
  allowed: false,
  reason: "Amount exceeds manager approval threshold",
  matchedRule: {
    id: 7,
    requiredRole: "franchise_owner",
    secondApprovalRole: "admin"
  }
}

PURPOSE
Avoid argument, ambiguity, and hidden rejection logic.

--------------------------------------------------
CRITICAL BUSINESS RULES
--------------------------------------------------

1. No refund approval without matching approval rule
2. No payout release without passing financial authority rules
3. Held money must remain visible as held, never hidden
4. Second approval must be enforced in backend, not UI only
5. Every approval decision must write to financial_approval_log
6. Financial controls must work for both:
   - franchise-owned stations
   - company-owned stations
7. Company-owned stations must never create fake franchise approval paths
8. Rules are data, not hardcoded
9. No silent overrides

--------------------------------------------------
DONE MEANS
--------------------------------------------------

- refund approvals are role-limited
- payout releases are role-limited
- dispute-related money can be held in reserve
- high-risk financial actions route into approval queue
- every approval is logged
- financial authority becomes explicit and enforceable
