#1 — FAKE PAYMENT ENDPOINT RETURNS SUCCESS WITHOUT CHARGING

Severity: CRITICAL | Legal/Compliance | Payment Risk

File: server/routes.ts:5156–5196

TypeScript
app.post('/api/express-checkout', async (req, res) => {
  // ...
  if (paymentMethod === 'credit_card') {
    // TODO: Integrate with real payment gateway
    // For now, just return success
    res.json({ success: true, message: "Express checkout successful", ... });
  }
});
/api/express-checkout accepts credit_card payment, returns { success: true }, and never charges anyone. There is no auth middleware, no Nayax call, no database write. If this endpoint is wired to any UI "Buy" button, users will believe they paid when they haven't. This is a fake payment flow that confirms purchases it never processes. Fix first.

#2 — TEST/CI AUTH BYPASS WITH HARDCODED DEFAULT TOKEN (AVAILABLE IN ALL NON-PROD ENVIRONMENTS)

Severity: CRITICAL | Security

File: server/middleware/firebase-auth.ts:43–48

TypeScript
const bypassToken = process.env.TEST_BYPASS_TOKEN || 'playwright-test';
if (bypassHeader === bypassToken) {
  return { uid: ..., email: `${uid}@test.local`, ... };
}
If TEST_BYPASS_TOKEN env var is not set, any HTTP client that sends x-test-user-bypass: playwright-test bypasses Firebase auth entirely and can impersonate any user. This is NOT guarded by NODE_ENV === 'production' (line 30 checks production only for the DEV_TEST_SECRET path, not the bypass token path). Anyone who knows this token — which is public in this codebase — can authenticate as any UID.

#3 — HARDCODED FALLBACK PAYMENT SECRETS (WEBHOOK & VOUCHER)

Severity: CRITICAL | Security

File: server/nayaxFirestoreService.ts:108–113

TypeScript
const VOUCHER_SALT     = process.env.VOUCHER_SALT              || 'pet-wash-nayax-voucher-secret-2025';

An attacker who knows the fallback salt can forge valid QR voucher tokens, bypassing payment. WEBHOOK_SECRET fallback means an attacker can forge Nayax webhook events (trigger credits/refunds).

#6 — ADMIN SECRET COMPARED WITH === (TIMING ATTACK)

Severity: HIGH | Security

Files: server/routes/financial-approvals.ts:28 and server/routes.ts:508, 11860

TypeScript
// financial-approvals.ts:28
if (req.headers['x-admin-secret'] === process.env.ADMIN_SECRET) {

// routes.ts:11860

#7 — MISSING PROVIDER OWNERSHIP VERIFICATION ON BOOKING ACCESS

Severity: HIGH | Security | IDOR

File: server/routes/super-app-bookings.ts:211–216

TypeScript
// SECURITY: Verify user ownership or provider access
if (booking.userId !== userId) {
  // Check if user is the provider
  // TODO: Add provider lookup to verify ownership

If the requesting user is not the booking customer, the code falls through to a 403 — regardless of whether they are the provider. Any authenticated user who isn't the customer will be blocked, including the actual service provider, but this also signals the authorization model is incomplete and may have gaps elsewhere.

#8 — WEBHOOK DEDUPLICATION IS IN-MEMORY ONLY (LOST ON RESTART)

Severity: HIGH | Payment Risk

File: server/routes/nayax-webhooks.ts:55–57

TypeScript
// In-memory deduplication cache (use Redis in production)
const processedWebhooks = new Set<string>();
const WEBHOOK_CACHE_TTL = 3600000; // 1 hour
Nayax webhook deduplication uses a JavaScript Set in process memory. On any server restart, crash, or horizontal scaling event, this cache resets. Nayax may retry unacknowledged webhooks, and after a restart the server will re-process them, resulting in duplicate credits, loyalty points, or session triggers. The comment acknowledges this: "use Redis in production."

#9 — XSS VIA dangerouslySetInnerHTML WITH BACKEND-SUPPLIED HTML

Severity: HIGH | Security

File: src/features/legal/LegalFrontend2025.tsx:409

TSX
dangerouslySetInnerHTML={{ __html: doc.htmlContent }}
The comment above it says: "Backend must sanitize HTML and remove unsafe elements." There is no evidence of HTML sanitization in the backend routes serving legal documents. If an admin can write to the legal documents table (or if that table is compromised), this is a stored XSS vector affecting all users who visit legal pages. Should use a server-side sanitizer (e.g., DOMPurify or sanitize-html) before storage and/or strip on render.

#10 — x-station-key IS THE ONLY AUTHENTICATION FOR MACHINE CONTROL ENDPOINTS

Severity: HIGH | Security

Files: server/routes.ts:4153–4160, 4230–4237, 4276–4283

TypeScript
app.post('/api/nayax/redeem', paymentLimiter, async (req, res) => {
  const stationKey = req.headers['x-station-key'] as string;
  // No user auth check — machine key is the only guard
K9000 station endpoints (/api/nayax/redeem, /api/k9000/start-session, /api/k9000/end-session) use only x-station-key header for auth — no user session. The station keys are stored in STATION_KEYS env var parsed as JSON. If any station key leaks (e.g., from a physical device), an attacker can trigger wash sessions, redeem vouchers, and manipulate station state without any user identity. #11 — WALLET BALANCE UPDATE HAS NO TRANSACTION/LOCKING (RACE CONDITION)

Severity: HIGH | Payment Risk

File: server/routes/walk-my-pet.ts:1878–1888

TypeScript
INSERT INTO wallet_accounts (wallet_id, user_id, cash_wallet_balance_cents)
  VALUES ($1, $2, $3)
  ON CONFLICT (user_id) DO UPDATE
    SET cash_wallet_balance_cents = cash_wallet_balance_cents + $1
The read–check–update pattern for wallet balance is not wrapped in a database transaction. Under concurrent requests (two simultaneous refunds, or a payment + refund arriving at the same time), both reads can see the old balance and both updates apply, resulting in double-crediting. This needs SELECT ... FOR UPDATE or a serializable transaction.

#15 — parseInt() / parseFloat() WITHOUT VALIDATION ON USER-CONTROLLED INPUTS

Severity: MEDIUM | Security | Stability

#18 — NO CSRF PROTECTION ON STATE-CHANGING ENDPOINTS

Severity: MEDIUM | Security

CSRF protection is implemented for WebAuthn only. All POST/PUT/DELETE routes — including /api/profile, /api/user/delete, booking mutations, and wallet operations — have no CSRF token requirement. The session cookie uses SameSite: strict in production (mitigates most CSRF), but API endpoints also accept Authorization: Bearer tokens from first-party JS, and any CORS misconfiguration would re-expose the attack surface.

#19 — VAT DISPLAYED/CALCULATED BUT RECEIPT WORDING MAY NOT SATISFY ISRAELI INVOICE LAW

Severity: MEDIUM | Legal/Compliance

Files: server/nayaxFirestoreService.ts:116–117, server/routes.ts:6462–6463, server/smartReceiptService.ts

Israeli invoice law (Heshbonim Law, 5775-2015) requires that VAT registration number, the seller's address, and an itemized VAT line appear on every invoice. The smart receipt stores vatAmount and vatRateUsed in the database but there is no verification that all of these required fields appear on the PDF/rendered receipt. The invoice number format INV-YYYYMMDD-XXXX (nanoid) also needs to be sequential and traceable per Israeli Tax Authority requirements.
