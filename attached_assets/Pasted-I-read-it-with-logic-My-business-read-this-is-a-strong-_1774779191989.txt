The first important risk

Customer timeline may be wrong if K9000 washes are anonymous

He already noticed this, and it is the most important unresolved point.

If a Nayax direct terminal wash is anonymous, then it must not appear in a customer timeline unless there is a real linked user identity.

So the rule should be:
	•	wallet / QR K9000 wash → can appear in customer timeline
	•	direct Nayax street payment with no user identity → must stay only in station timeline, not customer timeline

That is correct business logic.

Otherwise you risk showing customers machine events that do not belong to them.

The second important risk

Bay timeline query design is too optimistic

He suggested using:
	•	platform_events
	•	domain_events
	•	aggregate_id = bayId

That might work only if your event publishing is consistently writing bayId in exactly the same way everywhere.

That needs verification before building.

Safer rule:
	•	use bay_sessions as the primary truth for bay timeline
	•	use machine_commands for command lifecycle
	•	use bay_faults for fault history
	•	use bay_events as operational event log

Then only add domain_events if you already know the aggregate and payload mapping is consistent.

So I would not let him assume domain events are a clean bay feed until he proves it.

⸻

The third issue - execution priority

He says all 4 timeline endpoints can be built together.

Technically yes.
Business-wise, I would still force this order:
	1.	station timeline
	2.	bay event feed
	3.	provider timeline
	4.	customer timeline last

Why?

Because:
	•	station and bay views help operations immediately
	•	provider earnings view helps trust and payout visibility
	•	customer unified timeline is the most cross-domain and hardest to get fully correct

So customer timeline should come last, not first.
