PHASE 2.8C — ONE-CLICK SUPPORT ACTIONS

GOAL
Resolve the 3 highest-frequency support cases directly from the admin wallet dashboard:
1. release a stuck hold
2. issue a refund
3. grant manual wallet credit

These must be:
- admin-only
- fully ledgered
- idempotent
- reason-required
- tagged as support_action in metadata
- visible later in Action History and Audit Bundles

==================================================
BACKEND
==================================================

FILE
- server/routes/prestige-pass.ts

NEW ENDPOINTS

1) POST /api/prestige-pass/admin/wallet/support/release-hold
Body:
{
  "bookingId": "...",
  "bookingType": "marketplace" | "academy",
  "reason": "..."
}

Behavior:
- validate admin
- validate reason non-empty
- load booking from:
  - booking_requests if marketplace
  - trainer_bookings if academy
- require finance_state = 'hold_active'
- require wallet_hold_cents > 0
- call existing wallet release flow
- metadata:
  {
    adminId,
    reason,
    source: "support_action",
    supportAction: "release_hold",
    bookingType
  }
- update booking row:
  - finance_state = 'released'
  - wallet_release_key = returned txnId
- return:
  {
    ok: true,
    releasedCents,
    txnId,
    walletSnapshot
  }

2) POST /api/prestige-pass/admin/wallet/support/issue-refund
Body:
{
  "bookingId": "...",
  "bookingType": "marketplace" | "academy",
  "amountCents": 0,
  "reason": "..."
}

Rules:
- amountCents = 0 means full refundable amount
- validate admin
- validate reason
- load booking row
- if finance_state = 'debited':
  - refund from wallet
- if finance_state = 'hold_active':
  - treat as release, not refund
  - same endpoint can still succeed, but response should say actionTaken = "release"
- metadata:
  {
    adminId,
    reason,
    source: "support_action",
    supportAction: "issue_refund",
    bookingType
  }
- update booking row:
  - wallet_refund_key or wallet_release_key
  - wallet_refunded_cents if refund path
  - finance_state = 'refunded' or 'released'
- return:
  {
    ok: true,
    actionTaken: "refund" | "release",
    amountCents,
    txnId,
    walletSnapshot
  }

3) POST /api/prestige-pass/admin/wallet/support/credit
Body:
{
  "userId": "...",
  "amountCents": 0,
  "reason": "..."
}

Rules:
- validate admin
- validate amountCents > 0
- validate amountCents <= 50000
- call admin credit flow
- metadata:
  {
    adminId,
    reason,
    source: "support_action",
    supportAction: "manual_credit"
  }
- return:
  {
    ok: true,
    creditedCents,
    txnId,
    walletSnapshot
  }

==================================================
IMPORTANT BACKEND DESIGN RULES
==================================================

1. DO NOT invent a second financial path
All 3 endpoints must call the same wallet service / ledger methods already in production.

2. ACTION HISTORY COMPATIBILITY
Every support action must show up automatically in:
- Action History tab
- Action History CSV
- Audit Bundle
So metadata.source = "support_action" is mandatory.

3. IDEMPOTENCY
Use deterministic keys:
- wallet:support:release:<bookingType>:<bookingId>
- wallet:support:refund:<bookingType>:<bookingId>:<amount>
- wallet:support:credit:<userId>:<amount>:<daystamp>

4. SAFE STATE TRANSITIONS
- hold_active + release -> released
- hold_active + refund request -> released
- debited + refund -> refunded
- never allow refund when already refunded
- never allow release when no hold exists

ACCEPTANCE CHECKLIST
==================================================

1. Release stale hold
- create hold_active booking
- run support release
- finance_state becomes released
- pending balance returns
- action appears in Action History with support_action metadata

2. Refund debited booking
- create debited booking
- run support refund
- finance_state becomes refunded
- wallet_refunded_cents updated
- ledger row created
- action appears in Action History

3. Refund hold_active booking
- call refund endpoint on hold_active booking
- system performs release, not refund
- response actionTaken = "release"

4. Manual credit
- credit user with ₪50
- wallet balance increases
- ledger row visible
- action history visible

5. Duplicate submit
- same request repeated
- idempotent result returned
- no second money movement
