FINAL 2026 CAPTCHA ARCHITECTURE - COMPLETE IMPLEMENTATION

You are running a modern risk-based system using Google reCAPTCHA v3 with a secondary fallback (Cloudflare Turnstile or checkbox). This is a production-grade setup.

CORE FLOW:

User action  
→ reCAPTCHA v3 score  

Score handling:
- ≥ 0.7 → allow immediately  
- 0.4–0.69 → STEP_UP_REQUIRED  
- < 0.4 → block (bot-like traffic)  

STEP-UP FLOW (for suspicious users 0.4–0.69):

Primary step-up:
→ Phone OTP (Firebase or SMS)

Secondary fallback (if OTP fails or unavailable):
→ Cloudflare Turnstile (preferred) OR reCAPTCHA v2 checkbox  

FINAL FLOW:

User action  
→ reCAPTCHA v3  

≥ 0.7  
→ allow  

0.4–0.69  
→ STEP_UP_REQUIRED  
 → phone OTP (primary)  
 → Turnstile or checkbox (fallback)  

< 0.4  
→ block  

BACKEND LOGIC:

- All validation happens server-side  
- verifyCaptcha.ts returns:
  - CLEAN
  - SUSPICIOUS
  - BLOCKED  

- If SUSPICIOUS:
  - require step-up (OTP or Turnstile)

- If Turnstile token exists:
  - verifyTurnstile(token)
  - if valid → allow
  - if invalid → reject

- Never trust frontend flags  

FRONTEND FLOW:

Sign-in:
1. Get reCAPTCHA token  
2. Send to backend  
3. If STEP_UP_REQUIRED:
   - show Turnstile widget
   - retry request with turnstileToken  

Sign-up:
1. Pre-check score before Firebase user creation  
2. If suspicious:
   - show Turnstile
   - continue only after success  
3. Then create user + profile  

KEY COMPONENTS:

- verifyCaptcha.ts → score engine  
- verifyTurnstile.ts → fallback verification  
- TurnstileWidget.tsx → UI component  
- /api/recaptcha/check-score → pre-check endpoint

WITHOUT THESE:
