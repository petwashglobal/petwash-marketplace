PHASE 4.0 - OUTCOME INTELLIGENCE, SELF-HEALING & OPERATIONS COMMAND

GOAL
Move from fully observable orchestration into measurable, self-improving finance operations.
The platform should now:
- measure whether policies and automations actually created better outcomes
- classify which failures can self-heal safely
- expose approval bottlenecks quantitatively
- distribute governance outputs by audience and purpose
- compare scenario impact across entities
- group anomalies by likely root cause
- provide one command-level operational surface for finance

LOCKED PRINCIPLES
- no wallet-core changes
- no mutation of original financial facts
- all scoring must be explainable
- self-healing only applies to explicitly allowlisted failure classes
- bottleneck analytics must be read-only
- subscriptions and governance circulation must stay deterministic
- anomaly clustering is advisory first, never silently mutating
- command center actions must always route through existing audited workflows

==================================================
4.0A - POLICY OUTCOME & ROI SCORING
==================================================

GOAL
Measure whether policy changes and automations actually improved outcomes.

DB
Create table: policy_outcome_scores
- id SERIAL PRIMARY KEY
- policy_key VARCHAR(64) NOT NULL
- entity_code VARCHAR(32)
- evaluation_period_start DATE NOT NULL
- evaluation_period_end DATE NOT NULL
- baseline_json JSONB NOT NULL
- actual_json JSONB NOT NULL
- score_json JSONB NOT NULL
- roi_score NUMERIC(8,2) NOT NULL DEFAULT 0
- created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

Possible score_json fields:
- payout_delay_delta_hours
- refund_cycle_delta_hours
- dispute_breach_delta_pct
- anomaly_rate_delta_pct
- margin_delta_cents
- manual_intervention_delta_pct

BACKEND
1. GET /api/prestige-pass/admin/wallet/policy-outcomes?policyKey=&entityCode=&from=&to=
2. POST /api/prestige-pass/admin/wallet/policy-outcomes/recompute
3. GET /api/prestige-pass/admin/wallet/policy-outcomes/:policyKey/latest

Logic:
- compare pre-promotion baseline against post-promotion actuals
- compute weighted ROI score
- preserve metric-level breakdown

FRONTEND
Policies tab
- "Outcome Score" card per policy
- latest ROI badge
- before vs after metrics table
- recompute button
- entity filter

ACCEPTANCE
- same input period produces same score
- policy score is traceable to underlying metrics
- no scoring without closed-period actuals

==================================================
4.0B - SELF-HEALING ORCHESTRATION FOR SAFE FAILURE CLASSES
==================================================

GOAL
Allow the platform to retry safe classes of failures automatically.

DB
Create table: orchestration_retry_policies
- id SERIAL PRIMARY KEY
- run_type VARCHAR(64) NOT NULL
- error_pattern VARCHAR(255) NOT NULL
- auto_retry_enabled BOOLEAN NOT NULL DEFAULT true
- max_retries INTEGER NOT NULL DEFAULT 2
- retry_delay_minutes INTEGER NOT NULL DEFAULT 15
- enabled BOOLEAN NOT NULL DEFAULT true
- updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

Create table: orchestration_retry_attempts
- id SERIAL PRIMARY KEY
- orchestration_run_id INTEGER NOT NULL
- attempt_no INTEGER NOT NULL
- started_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
- completed_at TIMESTAMPTZ
- status VARCHAR(20) NOT NULL DEFAULT 'started'   // started | success | failed
- error_message TEXT NOT NULL DEFAULT ''

BACKEND
1. GET /api/prestige-pass/admin/wallet/orchestration-retry-policies
2. POST /api/prestige-pass/admin/wallet/orchestration-retry-policies
3. PATCH /api/prestige-pass/admin/wallet/orchestration-retry-policies/:id

JOB
- scans failed orchestration_runs
- matches run_type + error pattern
- retries only allowlisted failures
Examples of safe retry classes:
- transient email send failure
- temporary downstream timeout
- retryable archive retrieval failure
Not safe:
- money movement ambiguity
- partial payout release uncertainty
- replay execution with unknown side effects

FRONTEND
Orchestration tab
- "Retry Policies" card
- policy table
- recent retry attempts table
- badge on runs: auto-retried / manual-only

ACCEPTANCE
- only allowlisted failures retry automatically
- retry attempts are logged separately
- unsafe failures remain manual

- generated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

1. GET /api/prestige-pass/admin/wallet/approval-bottlenecks?from=&to=
Returns:
- avg_time_to_first_approval_hours
- avg_time_to_final_approval_hours
- by_chain_type[]
- by_approver[]
- stuck_requests[]
- top_bottleneck_stage

2. GET /api/prestige-pass/admin/wallet/approval-bottlenecks/:requestId
- step timeline for one approval request

FRONTEND
Policies or Orchestration tab
- bottleneck KPI tiles
- table by chain type
- approver leaderboard
- stuck request list
- click-through to per-request timeline

ACCEPTANCE
- metrics derive from approval_request_actions timestamps
- stuck requests use consistent thresholds
- no mutations

3. PATCH /api/prestige-pass/admin/wallet/governance-pack-subscriptions/:id

FRONTEND
Governance tab

- enable/disable

- include toggles

ACCEPTANCE

- top entity

==================================================
4.0F - ANOMALY ROOT-CAUSE CLUSTERING
==================================================

GOAL
Group anomalies into probable operational causes instead of flat lists.

DB
Create table: anomaly_clusters
- id SERIAL PRIMARY KEY
- cluster_key VARCHAR(128) UNIQUE NOT NULL
- root_cause_label VARCHAR(128) NOT NULL
- signal_codes JSONB NOT NULL
- confidence_score NUMERIC(5,2) NOT NULL DEFAULT 0
- last_seen_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
- created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

BACKEND
1. GET /api/prestige-pass/admin/wallet/anomaly-clusters
2. POST /api/prestige-pass/admin/wallet/anomaly-clusters/recompute
Logic:
- cluster by shared booking/provider/entity patterns
- likely labels:
  - payout data mismatch
  - stale hold lifecycle gap
  - dispute routing backlog
  - reconciliation import mismatch
  - remittance delivery gap

FRONTEND
Control Center tab
- "Root Cause Clusters" card
- grouped anomalies with confidence badge
- linked source anomalies
- recompute button

ACCEPTANCE
- same anomaly set clusters deterministically
- clustering is advisory and does not mutate source anomalies
- cluster labels are visible and explainable
