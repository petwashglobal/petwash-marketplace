PHASE 3.0 - FINANCE OPERATIONS & INSTITUTIONAL LAYER

CORE PRINCIPLE
Everything anchors on payout_batch_id as the finance object of record.

==================================================
3.0A - PAYOUT BATCH ENGINE
==================================================

GOAL
Turn "mark-paid" into a first-class batch system with exports, totals, and traceability.

DB
Create table: payout_batches

Columns:
- id SERIAL PRIMARY KEY
- batch_id VARCHAR(64) UNIQUE NOT NULL
- created_by_uid VARCHAR(128) NOT NULL
- created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
- status VARCHAR(20) NOT NULL DEFAULT 'open'  // open | exported | completed
- total_providers INTEGER NOT NULL DEFAULT 0
- total_net_cents INTEGER NOT NULL DEFAULT 0
- notes TEXT NOT NULL DEFAULT ''

BACKEND
1. POST /api/prestige-pass/admin/wallet/payout-batches/create
Input:
{
  "entryIds": [1,2,3],
  "notes": "Weekly payout"
}
Logic:
- validate all selected payout entries are eligible
- generate one batch_id
- mark entries as paid
- assign same payout_batch_id to all rows
- compute totals
- return batch summary

2. GET /api/prestige-pass/admin/wallet/payout-batches
Returns list of batches, newest first

3. GET /api/prestige-pass/admin/wallet/payout-batches/:batchId
Returns:
- batch header
- entries
- grouped providers
- totals

4. GET /api/prestige-pass/admin/wallet/payout-batches/:batchId/export
CSV columns:
provider_uid
division_code
booking_id
gross_ils
commission_ils
net_ils

FRONTEND
AdminWalletDashboard
- new "Payout Batches" tab
- batch list
- create batch modal
- export button
- totals cards

ACCEPTANCE
- same batch create request is idempotent
- batch export matches DB exactly
- totals equal sum of all entries

==================================================
3.0B - PROVIDER REMITTANCE & STATEMENTS
==================================================

GOAL
Providers get a clean statement for what they were paid and why.

BACKEND
1. GET /api/prestige-pass/provider/wallet/payout-statement?batchId=...
Returns:
- provider batch entries
- grouped by booking
- gross / commission / net totals

2. GET /api/prestige-pass/admin/wallet/payout-batches/:batchId/provider-export
Grouped provider export for ops/finance

FRONTEND
Provider Dashboard
- "Download Statement" button
- statement by batch
- booking-level breakdown

ACCEPTANCE
- provider sees exact paid numbers
- statement matches admin export

==================================================
3.0C - DISPUTE TO FINANCIAL ACTIONS BRIDGE
==================================================

GOAL
Disputes can result in refund or payout adjustment without ad hoc logic.

DB
Extend dispute_cases with:
- linked_payout_batch_id VARCHAR(64)
- resolution_action VARCHAR(20) DEFAULT 'none'   // refund | clawback | none

BACKEND
POST /api/prestige-pass/admin/wallet/disputes/:caseRef/apply-resolution

Logic:
- refund:
  - route through refund approvals flow from 2.9D
- clawback:
  - never mutate original payout row
  - create negative payout entry or future offset entry
- write audit metadata
- keep full trail

FRONTEND
Disputes tab
- "Apply Resolution" section in case drawer
- choose refund or reduce provider payout
- show resulting finance action state

ACCEPTANCE
- no direct mutation of original payout rows
- every resolution leaves immutable audit trail

==================================================
3.0D - DAILY CLOSE NOTIFICATIONS
==================================================

GOAL
Enforce close discipline without manual memory.

BACKEND JOB
Runs hourly.

If today's close record is still open:
- send reminder at 18:00 IL
- send reminder at 20:00 IL
- send reminder at 22:00 IL

Payload:
- checklist status
- blockers
- open anomalies count
- pending approvals count
- pending disputes count

DELIVERY
- email first
- optional SMS if needed later

ACCEPTANCE
- reminders stop immediately once day is closed
- no duplicate reminders for same checkpoint

==================================================
3.0E - FINANCE CLOSE EXPORT BUNDLE
==================================================

GOAL
Download one audit pack per day for compliance and finance review.

BACKEND
GET /api/prestige-pass/admin/wallet/finance-close/:date/export

Bundle contents:
1. settlement-summary.csv
2. payout-batches.csv
3. action-history.csv
4. anomaly-log.json
5. dispute-summary.csv

SIGNATURE
- SHA-256 hash of bundle manifest and files
- deterministic output

ACCEPTANCE
- same date exported twice with same underlying data yields same hash
- bundle opens cleanly and matches dashboard numbers

==================================================
3.0F - MONTH-END FINANCE PACK
==================================================

GOAL
One monthly pack for accountants and management.

BACKEND
GET /api/prestige-pass/admin/wallet/monthly-pack?month=2026-03

Returns:
{
  "collected": ...,
  "payouts": ...,
  "vat": ...,
  "margin": ...,
  "disputes": ...,
  "refunds": ...,
  "batches": ...
}

EXPORTS
- JSON
- CSV summaries

FRONTEND
Finance tab
- month selector
- "Download Month Pack" button

ACCEPTANCE
- monthly totals reconcile to daily closes
- no drift between daily and monthly math

==================================================
3.0G - ROLE-BASED FINANCE PERMISSIONS
==================================================

GOAL
Separate finance powers cleanly.

ROLES
- finance_admin: full access
- support: support actions only
- reviewer: refund approvals only
- read_only: dashboards only

BACKEND
Per-endpoint middleware:
- finance_admin for batching, close, exports, reversals
- reviewer for approval actions
- support for support actions
- read_only for viewing only

ACCEPTANCE
- support cannot approve refunds
- reviewer cannot credit wallets
- read_only cannot mutate anything

==================================================
BUILD ORDER
==================================================

1. 3.0A - payout batches
2. 3.0B - provider statements
3. 3.0C - dispute to finance bridge
4. 3.0D - daily close notifications
5. 3.0E - finance close export bundle
6. 3.0F - month-end finance pack
7. 3.0G - permissions

==================================================
LOCKED RULES
==================================================

- payout_batch_id is the anchor object for finance operations
- no wallet-core changes
- no mutation of original payout entries after payment
- all dispute financial outcomes create new immutable records
- close notifications are reminders only, never auto-close
- exports must be deterministic
- monthly pack must reconcile to daily closes
- permissions enforced server-side only, never UI-only

==================================================
WHAT THIS UNLOCKS
==================================================

After Phase 3.0:
- batch-based payouts
- provider statements
- dispute to refund or clawback linkage
- close-of-day discipline
- exportable finance bundles
- month-end reporting
- finance permission hardening

This gives you a finance layer that operators can run, accountants can trust, and auditors can verify.
