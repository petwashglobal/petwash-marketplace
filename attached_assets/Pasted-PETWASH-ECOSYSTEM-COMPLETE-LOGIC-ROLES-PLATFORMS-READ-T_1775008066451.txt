PETWASH ECOSYSTEM - COMPLETE LOGIC + ROLES + PLATFORMS
READ THIS BEFORE WRITING ANY CODE

If you misunderstand this document, you will build the wrong system.

This is not one app.
This is a multi-platform business with different users, different permissions, and different behaviors.

You must understand ALL parts before implementing ANY part.

=====================================
1. BIG PICTURE - WHAT WE ARE BUILDING
=====================================

PetWash is a unified system that connects:

- physical dog wash kiosks (real machines)
- mobile/web application (users + providers)
- internal SaaS (support + management)
- marketplace (services like grooming, walking, sitting)
- loyalty club (wallet + discounts)

Everything is connected to ONE backend.

The backend is the brain.
Everything else is just an interface.

=====================================

You must NEVER mix these.

SYSTEM OF RECORD

=====================================
3. USER TYPES (VERY STRICT)
=====================================

You MUST separate these completely.

-------------------------------------
1) CLIENTS (PUBLIC USERS)
-------------------------------------

These are pet owners.

What they do:
- register quickly
- no KYC
- get wallet
- get 5% discount
- some get 10% (manual approval)

Use cases:
- use kiosks
- buy packages
- manage wallet

They must NOT:
- upload ID
- go through provider flow
- see admin data

-------------------------------------
2) PROVIDERS (PROFESSIONALS)
-------------------------------------

These are service providers.

Types:
- groomers
- dog walkers
- pet sitters
- trainers
- mobile service providers

-------------------------------------

Before approval:
- must pass KYC
- upload selfie + ID

After approval:
- can work in system
- can offer services (future)

-------------------------------------

IMPORTANT:
Providers are HIGH TRUST.
KYC is mandatory.

-------------------------------------
3) TRAINEES (NEW / LIMITED PROVIDERS)
-------------------------------------

These are beginner providers.

Rules:
- may have limited permissions
- may require extra review
- may not be fully trusted yet

Examples:
- new groomers
- trainee walkers
- junior sitters

System must support:
- role differentiation
- limited access
- gradual upgrade

-------------------------------------
4) SUPPORT (OPERATIONS TEAM)
-------------------------------------

They run daily operations.

They can:
- review applications
- approve / reject
- request resubmission
- communicate with applicants
- assign queue items

They must NOT:
- change system logic
- access management analytics

-------------------------------------
5) MANAGEMENT
-------------------------------------

They do NOT operate daily tasks.

They:
- see analytics
- see trends
- see fraud patterns
- see performance

They must NOT:
- manually review every case

=====================================
4. PROVIDER ONBOARDING (CORE FLOW)
=====================================

STEP 1 - SUBMISSION
- user uploads selfie + ID
- data saved immediately
- status = submitted

IMPORTANT:
NEVER block on external APIs.

-------------------------------------

STEP 2 - PROCESSING (ASYNC)
- KYC2026 runs
- face match
- liveness
- OCR
- quality check

-------------------------------------

STEP 3 - SYSTEM DECISION

Possible:
- approved
- rejected
- pending_review
- pending_resubmission

-------------------------------------

STEP 4 - HUMAN REVIEW (IF NEEDED)
Support:
- opens application
- sees everything
- decides

-------------------------------------

STEP 5 - FINAL STATE
- provider activated
OR
- rejected
OR
- resubmitted

=====================================
5. BUSINESS RULES (CRITICAL)
=====================================

- Backend is ALWAYS authority
- KYC is advisory only
- No frontend decisions
- Everything logged
- No silent failures
- Every state must be explainable
