PHASE 3.9 - ORCHESTRATION RESILIENCE & GOVERNANCE SCALE

GOAL
Harden orchestration into a fully observable, controllable, and scalable system.
The platform should now:
- monitor all automated executions in real time
- prevent unsafe promotions before they go live
- reuse proven scenarios instead of recreating them
- manage assistant-driven execution through queues
- control who receives governance outputs and when
- make all reporting entity-aware
- provide full end-to-end orchestration traceability

LOCKED PRINCIPLES
- no silent execution - every automated action must be observable
- no unsafe promotion - every policy promotion must pass validation checks
- no duplicated effort - scenarios should be reusable templates
- no direct assistant execution - always mediated by queue/approval
- no uncontrolled distribution - governance packs must follow rules
- entity support must remain additive and backward compatible
- full auditability across every orchestration step

==================================================
3.9A - ORCHESTRATION MONITORING & FAILURE RECOVERY
==================================================

GOAL
Track every automated execution and detect failures early.

DB
Create table: orchestration_runs
- id SERIAL PRIMARY KEY
- run_type VARCHAR(64) NOT NULL   // payout_release | replay | refund | assistant_action | policy_promotion
- entity_type VARCHAR(64)
- entity_id VARCHAR(128)
- status VARCHAR(24) NOT NULL     // started | success | failed | retrying
- error_message TEXT
- retry_count INTEGER NOT NULL DEFAULT 0
- started_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
- completed_at TIMESTAMPTZ
- metadata JSONB NOT NULL DEFAULT '{}'::jsonb

Indexes
- run_type
- status
- started_at DESC

BACKEND
1. Wrap all 3.8 execution paths:
- approval execution
- assistant execution
- policy promotion
- replay execution

Helper:
recordOrchestrationRun(start → success/fail → retry)

2. GET /api/prestige-pass/admin/wallet/orchestration-runs
Filters:
- runType
- status
- date range

3. POST /api/prestige-pass/admin/wallet/orchestration-runs/:id/retry
- finance_admin only
- retries failed execution

FRONTEND
New "Orchestration" tab
- live table of runs
- status badges
- retry button for failed runs
- expandable error detail

ACCEPTANCE
- every execution produces a run record
- failed runs are visible and retryable
- retries increment retry_count

==================================================
3.9B - PROMOTION SAFETY CHECKS & ROLLOUT GUARDS
==================================================

GOAL
Prevent unsafe policy promotions from simulations.

DB
Create table: promotion_validations
- id SERIAL PRIMARY KEY
- simulation_id INTEGER NOT NULL
- validation_type VARCHAR(64) NOT NULL   // risk_threshold | value_limit | anomaly_delta
- passed BOOLEAN NOT NULL
- detail TEXT
- created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

BACKEND
1. Extend:
POST /policy-simulations/:id/promote

Before promotion:
- run validations:
  - risk score < threshold
  - affected value < max limit
  - anomaly delta within safe range

If failed:
- block promotion
- return validation errors

2. GET /api/prestige-pass/admin/wallet/promotion-validations?simulationId=...

FRONTEND
Simulation tab
- "Validation Summary" panel before promote
- show pass/fail per rule
- disable promote button if failed

ACCEPTANCE
- unsafe simulations cannot be promoted
- validation results visible to user
- thresholds configurable via policy engine

3.9C - SCENARIO LIBRARY & TEMPLATE SYSTEM

2. POST /api/prestige-pass/admin/wallet/forecast-templates
3. POST /api/prestige-pass/admin/wallet/forecast-templates/:id/apply

FRONTEND
Simulation tab
- "Save as Template" button
- template library list
- "Apply Template" button to prefill scenario

ACCEPTANCE
- templates reproduce original scenario inputs
- applying template does not mutate original scenario
- templates can be disabled

==================================================
3.9D - ASSISTANT EXECUTION QUEUE & DELEGATION
==================================================

GOAL
Introduce queue-based execution for assistant actions.

DB
Create table: assistant_execution_queue
- id SERIAL PRIMARY KEY
- action_type VARCHAR(64) NOT NULL
- payload JSONB NOT NULL
- requested_by_uid VARCHAR(128)
- assigned_to_uid VARCHAR(128)
- status VARCHAR(24) NOT NULL DEFAULT 'queued'   // queued | in_progress | approved | rejected | executed
- created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
- updated_at TIMESTAMPTZ

BACKEND
1. POST /assistant/execute → now pushes to queue
2. GET /assistant/queue
3. POST /assistant/queue/:id/assign
4. POST /assistant/queue/:id/approve
5. POST /assistant/queue/:id/execute

FRONTEND
Governance tab
- "Assistant Queue" section
- assign dropdown
- approve/reject buttons
- execution status

ACCEPTANCE
- assistant actions never execute immediately
- queue controls flow
- assignment and approval tracked

3.9E - GOVERNANCE RECIPIENT GROUPS & DISTRIBUTION RULES
==================================================

GOAL
Control governance pack distribution centrally.

DB
Create table: governance_recipient_groups
- id SERIAL PRIMARY KEY
- group_name VARCHAR(128) NOT NULL
- recipients JSONB NOT NULL   // list of emails or user_uids
- enabled BOOLEAN NOT NULL DEFAULT true
- created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

Create table: governance_distribution_rules
- id SERIAL PRIMARY KEY
- pack_type VARCHAR(32) NOT NULL
- group_id INTEGER NOT NULL
- schedule VARCHAR(32) NOT NULL   // weekly | monthly | manual
- enabled BOOLEAN NOT NULL DEFAULT true

BACKEND
1. GET /governance/recipient-groups
2. POST /governance/recipient-groups
3. GET /governance/distribution-rules
4. POST /governance/distribution-rules

Integrate with:
- governance pack send job

FRONTEND
Governance tab
- "Recipient Groups" panel
- "Distribution Rules" panel

ACCEPTANCE
- packs only sent to configured groups
- rules control cadence
- manual send still allowed

ACCEPTANCE
