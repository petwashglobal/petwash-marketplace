What Was Fixed (9 Code Changes — All Committed)

1. CRITICAL — Google Mobile Login Creates Orphan Users

Root cause: mobile-auth.ts only created a Firestore profile + wallet row via raw SQL. No PostgreSQL users row was ever inserted. Every downstream query (SELECT * FROM users WHERE id = uid, quote engine, loyalty page, booking creation) silently failed or returned nulls.
Fix: Replaced the raw pool.query wallet insert with authService.ensureUserInPostgres() which atomically creates the users row, loyalty_profiles row, and wallet_accounts row. Also runs idempotently for existing users so re-login is safe.

2. HIGH — Wallet Credit Had No 50% Cap (Financial Discrepancy)

Root cause: Loyalty credits were correctly capped at 50% of subtotal, but wallet cash/promo/referral credits had no cap — a user with ₪1000 wallet balance could zero out a ₪300 booking entirely.
Fix: Added Math.floor(subtotal * 0.5) cap to the wallet credit block in quoteEngine.ts, matching loyalty behavior.

3. HIGH — Provider Notification Was In-App Only

Root cause: When a booking request was created, dispatchNotification was called with channels: ['in_app'] only — providers who weren't looking at the app never saw it.
Fix: Now looks up the provider's email and phone from the users table and passes all three channels (in_app, email, sms) with a proper bilingual HTML email body and CTA link.

4. HIGH — Provider Approval Always Claims emailSent: true

Root cause: The admin approval response hardcoded emailSent: true even when the EmailService.send() threw an exception. Admins had no way to know the invitation email failed.
Fix: Tracks real send result in invitationEmailSent boolean; response now accurately reflects emailSent: false and includes emailNote for the admin UI when delivery failed.

5. HIGH — Provider Can't Access Dashboard After Approval (Claims Propagation)

Root cause: Firebase custom claims are set server-side on approval, but the provider's frontend session token doesn't know to refresh — they see "pending" dashboard for up to 30+ minutes until their token naturally expires.
Fix: Added an in-app notification (actionType: 'force_token_refresh') delivered immediately on approval. The frontend notification listener should call user.getIdToken(true) when it sees this type, which forces an immediate token refresh so claims propagate instantly.

6. MEDIUM — onboardingCases Duplicate Rows on Double-Submit

Root cause: complete-registration.ts had no guard against concurrent or retry submissions — two simultaneous requests could create two rows with the same email+context.
Fix: Added a SELECT check before INSERT; if a case already exists for this email it skips the insert and proceeds (idempotent).

7. MEDIUM — Loyalty Auto-Enroll Didn't Create Wallet for Google Users

Root cause: POST /api/loyalty/auto-enroll created a loyalty_profiles row but never created a wallet_accounts row. Google/Apple/Facebook users who hit this path had no wallet, causing silent failures at checkout.
Fix: Added authService.ensureWalletAccount(userId) (non-blocking fire-and-forget) at the end of the auto-enroll handler.

8. HIGH — Cancellation Reason Not Validated

Root cause: req.body.reason was inserted raw into statusHistory and cancellationReason with no length or content validation.
Fix: Added typeof check, .trim(), and .slice(0, 500) before use.

9. MEDIUM — Booking Calendar Showed Dead-End When No Slots

Root cause: When a provider had no availability slots, the calendar showed "No available slots for this date" with only a Retry button — the user was completely stuck.
Fix: Added onRequestCustomDate optional prop to BookingCalendar; MarketplaceBookingFlow passes a handler that activates customDateMode — shows a MobileDatePicker for the user to enter any date/time, sets a sentinel lockToken to unlock the Next button, and the booking is submitted as a manual request (which the backend already fully supports via createBookingRequestSchema).

What Still Needs Architectural / Operator Work

These require infrastructure decisions, credentials, or larger refactors that go beyond safe single-session changes:

🔴 CRITICAL — No Background Check (Rover/Madpaws Standard)

The backgroundCheckStatus, criminalCheckStatus, criminalCheckProvider columns exist in the DB but the entire stage (background_check_pending) is defined and never executed. No Checkr or equivalent API is integrated. Providers are approved based on KYC alone — no criminal history check. This is a legal and safety compliance risk for a pet-care marketplace in Israel.
What to do: Integrate Checkr (international) or a local Israeli background check provider into the stage after documents_under_review.

🔴 CRITICAL — KYC Liveness Check Is Not ISO-Certified

The liveness check is a 6-signal heuristic (pose, blur, size, expression, confidence, lighting) that is explicitly marked "Heuristic only — NOT ISO 30107-3 certified" in the code. It can be bypassed with a high-quality printed photo. Under Israeli Privacy Law 2025 §14 and GDPR Art. 9, biometric processing requires certified-grade liveness detection.
What to do: Replace with a certified vendor (Jumio, Persona, iDenfy, or similar).

🔴 CRITICAL — KYC Documents Not Encrypted at Rest

Government IDs and biometric selfies are stored as plain files in GCS. If the bucket ACL is misconfigured they are publicly readable.
What to do: Enable GCS Customer-Managed Encryption Keys (CMEK) and set DOCUMENT_ENCRYPTION_KEY env var — the code already references it but it was never configured.

🔴 CRITICAL — Double Wallet-Hold Race Condition

Two simultaneous booking requests from the same user against different providers both create separate idempotency keys (wallet:booking:hold:{bookingId1} and wallet:booking:hold:{bookingId2}), so both holds can succeed even if the wallet only has enough balance for one. This is in WalletLedger.ts inside holdWallet() — the fix requires a SELECT SUM(pending_holds) FOR UPDATE total-hold check before allowing a new hold.

🟠 HIGH — Provider Dashboard Lockout During Pending

Providers who submit an application see a blank "pending" message until approved. Rover and Madpaws both show a preview profile with a "Pending Approval" badge during review. This requires a new /provider/pending-profile page and a partial access Firebase claim (role: 'provider_pending').

🟠 HIGH — No Rejection Email Sent to Providers (Previous Session)

This was noted in the previous session and the rejection email for applications that reach admin_final_review → rejected was added in the prior commit. However the KYC auto-rejection (face score < 55) path in provider-onboarding.ts still sends no email to the provider — it only sets the DB status. That path needs the same sendLuxuryEmail call.

🟠 HIGH — No Email/SMS After Booking Accepted by Provider

When a provider accepts a booking the customer gets an in-app notification only. Both Rover and Madpaws send a confirmation email with: booking ID, provider name, date/time, amount, what to bring, and cancellation policy link. Wire dispatchNotification at the 'accept' branch of booking-requests.ts:POST /:requestId/respond with channels: ['in_app', 'email', 'sms'].

🟠 HIGH — No Provider Slot Generation on Onboarding

New providers complete 9 onboarding stages but are never guided to create availability slots. The calendar remains empty, customers see "No available slots", and now fall back to manual date requests — but providers still have to manually create recurring slots to appear in calendar search. Add a "Set your weekly schedule" step at stage approved → onboarding_complete that calls POST /api/provider-slots with a recurring template.

🟡 MEDIUM — Firebase Custom Claims Propagation (Frontend Side)

The backend now sends a force_token_refresh in-app notification on provider approval. The frontend notification listener needs to be updated to actually call user.getIdToken(true) when it sees actionType === 'force_token_refresh'. This is a client-side change in the notification display component (likely NotificationBell.tsx or AuthProvider.tsx).
