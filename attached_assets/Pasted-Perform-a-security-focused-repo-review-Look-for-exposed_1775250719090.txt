C-1 — Express Checkout Returns Payment Success Without Processing Any Payment

File: server/routes.ts:5179–5188

C-2 — Hardcoded Fallback Credentials in Nayax Payment Service

File: server/nayaxService.ts:70–72

TypeScript
private static readonly API_KEY     = process.env.NAYAX_API_KEY     || 'test_api_key';
private static readonly NAYAX_SECRET = process.env.NAYAX_SECRET     || 'test_secret';
private static readonly WEBHOOK_SECRET = process.env.NAYAX_WEBHOOK_SECRET || 'webhook_secret';
This class is actively called from server/routes/gift-cards.ts:313 for real gift card purchases. If any of the three env vars are missing in a deployment, the service silently falls back to these strings — which means it would attempt Nayax API calls with known-public credentials or fail in an unpredictable and unmonitored way. More importantly the webhook secret fallback ('webhook_secret') would cause signature validation to pass for any attacker who knows this literal string.

Action: Remove all three fallbacks. Hard-fail at startup if any are absent in production.

C-3 — Webhook IP Allowlist Fails Open When Env Var Is Not Set

Files: server/middleware/ipAllowlist.ts:157–163, server/routes/nayax-webhooks.ts:49–53

TypeScript
// ipAllowlist.ts
if (process.env.NODE_ENV === 'development' || allowedCIDRs.length === 0) {
  logger.warn(`IP allowlist not configured - allowing all IPs`);
  return next();   // ← ALL IPs ALLOWED
}
createIPAllowlist reads process.env.NAYAX_ALLOWED_IPS directly. If that variable is not set, allowedCIDRs is empty, the length === 0 branch fires, and the middleware calls next() in production — allowing any IP to send webhook events. The fallback array defined in nayax-webhooks.ts:49 is only a local constant and is never read by the middleware. The net result: if NAYAX_ALLOWED_IPS is absent from the deployment environment, the IP guard is silently disabled in production.

Action: Change the fail condition to hard-block in production when the env var is missing (return res.status(403)). Separately, verify NAYAX_ALLOWED_IPS is set in the production environment today.

C-4 — Webhook Deduplication Is In-Memory Only (Replay Attacks Survive Restarts)

File: server/routes/nayax-webhooks.ts:55–56

TypeScript
// In-memory deduplication cache (use Redis in production)
const processedWebhooks = new Set<string>();
Every server restart clears this Set. A Nayax webhook replayed within the TTL window (1 hour) after a restart will be processed again — duplicate payment confirmations, duplicate escrow creation, duplicate loyalty points. With Cloud Run or any horizontally scaled deployment each instance has its own in-memory Set, so the same event can hit two instances simultaneously and both process it.

Action: Move deduplication to the database. Insert the event ID into a processed_webhook_events table inside the same transaction as the business logic, with a unique constraint.
