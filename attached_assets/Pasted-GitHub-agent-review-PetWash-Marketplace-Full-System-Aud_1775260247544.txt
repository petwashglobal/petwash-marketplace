PetWash Marketplace — Full System Audit (April 2026)
This report covers Face ID/passkeys, admin access control, all API integrations, booking wiring, storage/backups, and active hacker entry points — building on the signup/provider analysis from the first session.

1 — FACE ID AND PASSKEYS (WebAuthn)
Architecture
There are two separate biometric systems that must not be confused:
	•	System A — Passkey/WebAuthn login: Device Face ID or fingerprint used to sign in (via platform authenticator on iOS/Android).
	•	System B — KYC face matching: Google Cloud Vision API comparing selfie to government ID for provider verification.
Critical Passkey Bugs
Bug P1 — Two conflicting WebAuthn implementations (CRITICAL) server/routes/webauthn.ts and server/routes.ts (lines 2760–2880) both define WebAuthn registration and login endpoints. They use different challenge storage backends (Firestore vs signed cookies). The client calls one; the other silently does nothing. One path may have security gaps that the other doesn't. There is no single source of truth.
Bug P2 — Challenge not stored server-side in /register/options (HIGH) server/routes/webauthn.ts:104 — The registration options endpoint generates a challenge and returns it to the client without storing it in the database. The verification step has no way to confirm the challenge was server-issued. An attacker who intercepts the challenge can replay it within the 5-minute window.
Bug P3 — /authenticate/verify has no auth middleware (HIGH) server/routes/webauthn.ts:256 — The authentication verification endpoint accepts any email and retrieves the Firebase user without requiring a prior session. This enables email enumeration: an attacker can probe any address and learn whether it has passkeys registered.
Bug P4 — Apple and Android attestation validation not implemented (HIGH) server/webauthn/config.ts:337–367 — Both validateAppleAttestation() and validateAndroidAttestation() are stubs that always return true. There is no certificate chain verification, no SafetyNet/Key Attestation check for Android, and no Apple App Attest check. Any device — including emulators and non-genuine hardware — can register passkeys.
Bug P5 — Credential storage split across three backends (MEDIUM) Passkey credentials are written to Firestore, to a JSONB column in the userstable, and partially referenced in shared/schema.ts. There is no single authoritative store. A deleted Firestore document would leave an orphaned PostgreSQL record, causing login failure with no recovery path.
Bug P6 — Server reads VITE_FIREBASE_PROJECT_ID (client env var) for biometric bucket (MEDIUM) server/infra/biometricStorage.ts:14 — This server-side file uses the browser-prefixed env var. In environments where only server vars are set, the bucket name falls back to the hardcoded string "signinpetwash", pointing to the wrong GCS project.

4 — API INTEGRATIONS STATUS
Google Maps — API Key Exposed to Browser
server/routes.ts:659 reads process.env.VITE_GOOGLE_MAPS_API_KEY. The VITE_ prefix means this value is bundled into the client JavaScript and visible in any browser's developer tools or network inspector. Google Maps is a billable API. An exposed key can be used by anyone to run up charges. The fix is to use GOOGLE_MAPS_API_KEY (no VITE prefix) server-side only, and proxy map requests through the server rather than exposing the key to the browser.
Google Drive Backup — No Encryption
server/services/googleDriveBackupService.ts:176 — Backup files are uploaded as raw JSON.stringify() output. The backup contains invoices, digital signatures, biometric certificate records, provider applications, and security events. If the Google Drive account or service account is compromised, all this data is readable immediately. Backup data should be encrypted with AES-256 before upload.
Google Drive Backup — Silent Failure
server/services/googleDriveBackupService.ts:192–197 — Backup errors are caught and logged but no alert is sent (no email, no SMS, no Slack). Backups can fail silently for weeks with no visibility.
Google Sheets — 25+ Sheets Including Sensitive Data
server/services/googleSheetsIntegration.ts:14–51 — Sheet names include IDENTITY_VERIFICATIONS, SECURITY_EVENTS, CONSENT_AUDIT, E_SIGNATURES. These contain PII. Sheets are accessible to anyone with the service account, and they are stored unencrypted.
SendGrid
server/emailService.ts — Well implemented overall:
	•	✅ API key validated at startup
	•	✅ HTML sanitization with sanitize-html and allowlist
	•	✅ Rate limited: 100/hour and 500/day per recipient
	•	⚠️ Rate limits are in-memory only — reset on server restart (TODO comment at line 24 acknowledges this)
	•	✅ Consent and unsubscribe enforced
	•	✅ Gmail fallback on SendGrid failure (but this can mask outages)
SMS / Twilio
server/services/RegistrationOTPService.ts and server/services/TwilioSMSService.ts — Reasonably well implemented:
	•	✅ OTP hashed with SHA-256, constant-time comparison
	•	✅ 3 OTP sends per phone per hour; 15 per IP per hour; 60-second cooldown
	•	✅ 5 verification attempts max then 15-minute lockout
	•	✅ Approved-countries allowlist (no high-risk regions)
	•	⚠️ reCAPTCHA/Turnstile is non-blocking — if it fails, the request proceeds anyway. This means CAPTCHA is decoration, not protection.
	•	⚠️ Phone numbers are cleaned but not validated for SMS injection characters before being passed to the Twilio API
Google Calendar
server/services/GoogleCalendarIntegrationService.ts — OAuth2 refresh token pattern used. Requires GOOGLE_BUSINESS_CLIENT_ID, GOOGLE_BUSINESS_CLIENT_SECRET, GOOGLE_BUSINESS_REFRESH_TOKEN. Not deeply broken but these env vars have no startup validation — if missing, Calendar events will silently fail to create.
Weather APIs
Five weather providers (OpenWeather, WeatherAPI, Visual Crossing, AQICN, Ambee) are configured with graceful degradation. If all keys are missing, the service returns null rather than crashing. This is acceptable.
Nayax (Payment)
	•	✅ Webhook HMAC-SHA256 signature validation
	•	✅ IP allowlist enforced
	•	⚠️ Dedup cache TTL is 1 hour — replay attacks possible after 1 hour using the same webhook
	•	⚠️ No test-vs-production key separation visible — risk of prod accidentally pointing to test environment

5 — BOOKING SYSTEM WIRING
PawSpa Platform Does Not Exist
Zero references to "PawSpa" anywhere in the codebase. If this platform is intended to exist, it has not been implemented.
Octopus V1 Bookings Are Deprecated But Still Reachable
server/routes/octopus-engine.ts:78–80 — All V1 booking endpoints return a deprecation warning and log the call, but they still process the request. Old clients or integrations that haven't migrated still work but go through unmaintained code.
/api/k9000 Registered Three Times With Different Middleware
server/routes.ts:9751, 9754, 9757 — Express uses the first matching mount. Lines 9754 and 9757 may be unreachable. The adminLimiter and optionalFirebaseToken middleware on those lines is never applied.
walkMyPetRoutes Mounted at /api (Too Broad)
server/routes.ts:10017 — app.use('/api', apiLimiter, walkMyPetRoutes) mounts the Walk My Pet router at the root API path, not just at /api/walk-my-pet. Express matches this AFTER more specific routes (because they are registered first), so it should not shadow them in normal operation. However, any Walk My Pet route that matches a path used by another module would collide, and this is a maintenance trap that will cause hard-to-debug conflicts.
Payment Has No Idempotency Key
server/routes/booking-requests.ts:985–1134 — The /pay endpoint calls EscrowService.createEscrowPayment() with no idempotency key and no check for whether a payment transaction ID already exists. If a network timeout causes the client to retry, the user is charged twice.
No Atomic Database Transactions
No BEGIN/COMMIT/ROLLBACK patterns found in booking payment flows. If the escrow is created at line 1030 and the booking status update at line 1063 fails, the funds are held in escrow with no associated booking status. There is no rollback.

7 — GENERAL SECURITY VULNERABILITIES
CORS with Credentials
server/index.ts:91–133 — CORS is configured with credentials: true. If the origin validation function ever returns a wildcard * on error (lines 97, 106), the combination of credentials: true and origin: * is invalid per the CORS spec and browsers will block the response. More importantly, any misconfiguration in the origin function could allow a malicious domain to make credentialed cross-site requests.
No SQL Transactions Anywhere
Searches across the entire server/ directory find no BEGIN, COMMIT, or ROLLBACK SQL statements and no Drizzle transaction wrappers. Multi-step operations (payment + booking creation, user creation + loyalty setup, escrow creation + status update) are all vulnerable to partial failure leaving the database in an inconsistent state.
reCAPTCHA Is Non-Blocking on OTP
server/routes/publicAuthRoutes.ts:315–316 — If reCAPTCHA validation fails, the code logs a warning and continues. This makes reCAPTCHA useless as an anti-bot measure for OTP sending. An attacker's bot just needs to send the OTP request without a valid CAPTCHA token and it works anyway.

Highest-Priority Fixes (Ordered by Blast Radius)
	1	Fix 14 SQL injection vulnerabilities in prestige-pass.ts — use Drizzle sql tagged templates or $1/$2 parameters. These allow arbitrary data exfiltration today.
	2	Enforce phone-based 2FA for admin login and remove all hardcoded admin emails from source code — move to SUPER_ADMIN_EMAILS environment variable exclusively.
	3	Use timingSafeEqual() on all x-admin-secret comparisons in teams.ts, booking-trace.ts, case-queue.ts, case-actions.ts, station-dashboard.ts.
	4	Create a single shared registerUserPostAuth(uid, provider, email) function called by every auth path that: creates the PostgreSQL user row, creates the wallet, creates the loyalty profile. This fixes the Facebook/Instagram/TikTok/email inconsistency in one change.
	5	Make reCAPTCHA blocking on OTP send — return 400 if CAPTCHA fails rather than proceeding.
	6	Encrypt Google Drive backup files before upload with AES-256, and add an alert (email/SMS) on backup failure.
	7	Fix passkey duplicate implementations — choose one (prefer server/routes.ts unified service), add requireAuth to /authenticate/verify, and implement challenge storage in /register/options.
	8	Add an idempotency key to the payment endpoint — check for existing paymentTransactionId before charging, and wrap the escrow + booking update in a database transaction.
	9	Remove VITE_GOOGLE_MAPS_API_KEY from server code — use GOOGLE_MAPS_API_KEY (server-only) and restrict the Maps API key to your server's IP in Google Cloud Console.
	10	Add limits: { fileSize: 10 * 1024 * 1024 } to the careers.ts multer config to prevent memory exhaustion.
