GOAL
Build a 2026-grade, legally safe, fintech-level onboarding and auth system for the platform at petwash.co.il where:
- Customers, loyalty members, providers, staff, and admins have different sign up intents
- Each intent routes to the correct onboarding
- Phone login supports flags + country code + number (default Israel, allowlisted countries)
- Passkeys (Face ID / Touch ID) are first-class
- Every profile is completed (DOB, name, address, ID/passport) according to role and law
- Everything is saved reliably (DB is source of truth, Sheets optional mirror)
- No “99%” - enforce completeness and compliance server-side

--------------------------------------------------------------------
1) FIX THE CORE PRODUCT LOGIC: INTENT-BASED SIGN UP AND ROUTING
Problem:
Right now OAuth or phone sign up lands everyone in the same place. That breaks role logic.

Solution:
Introduce a required “Intent” before auth, stored and passed through the auth callback.

INTENTS (example)
- customer: book services
- loyalty: join rewards club
- provider: apply as sitter/walker/host
- staff: internal staff access (request)
- admin: management console (invite only)

UI CHANGE (signin modal)
- Step 1: choose intent (cards)
- Step 2: choose auth method (Google/Apple/Phone/Passkey etc)
- Persist intent in:
  - localStorage: signup_intent
  - also pass via OAuth state param if possible

SERVER RULE
- After Firebase auth success, backend creates or loads DB user profile
- Then server decides redirect based on intent + existing profile status

Redirect matrix:
- customer -> /onboarding/customer
- loyalty -> /onboarding/loyalty
- provider -> /onboarding/provider
- staff -> /request-access (then pending)
- admin -> /admin-access (invite only, pending until approved)

Never guess intent from email provider. Intent must be explicit.

--------------------------------------------------------------------
2) MAKE ONBOARDING A STATE MACHINE (NOT A PAGE)
Problem:
Users can enter the app with missing required data, causing failures later.

Solution:
Create a single “Onboarding Router” that checks completeness server-side on every protected action.
- If incomplete -> force redirect to the next required step.
- This must be enforced by backend middleware, not only frontend.

Profile status fields:
- profileStatus: "incomplete" | "pending_review" | "active" | "rejected" | "suspended"
- onboardingStep: string (next required step id)
- intent: customer|loyalty|provider|staff|admin

Next-step algorithm:
- Compute required fields by role
- If missing -> set onboardingStep -> return {nextUrl}
- Frontend always obeys nextUrl

Example middleware behavior:
- For any non-GET booking, wallet, provider routes:
  - requireAuth
  - requireEmailOrPhoneVerified
  - requireOnboardingComplete(for route role)
  - requireMFA(for admin roles)
  - allow only if status active/pending_review depending on route

3) SEPARATE ROLE REQUIREMENTS (WHAT DATA IS REQUIRED)
Customer minimum (to book):
- fullName
- email OR phone (verified)
- country, city
- consent flags (privacy, terms)
Optional: address for at-home services

Loyalty member minimum:
- everything in customer minimum
- DOB (age check)
- marketing consent granular (SMS/email/push)
Optional: national ID only if you need KYC for wallet credits, refunds, or high-value redemptions

Provider (must be strict):
- legal full name
- DOB
- address (full)
- government ID/passport (number + images)
- selfie (match)
- profile photo (public)
- bank/payout details (if paying out)
- background check fields if required
- insurance acceptance / declarations
- agreement signatures (provider terms)
- status becomes pending_review until approved (or auto-approve only after full checks)

Staff/admin (invite and approval only):
- Must not be self-service sign up.
- Flow:
  1) user signs in
  2) backend sees role request staff/admin
  3) create access_request record
  4) notify approver (nir.h@...) with approve/deny
  5) until approved -> block all admin routes

4) PHONE LOGIN MUST BE INTERNATIONAL + FLAGS (DEFAULT IL, ALLOWLIST)
Problem:
Israel-only phone format breaks global onboarding.

Solution:
Use a phone input component with:
- flag on the left
- country code next
- number input
- default country IL
- allowlist only approved countries (IL, AU, US, GB, FR, DE etc)
- output must be E.164 always (example +61419...)

Frontend:
- Use libphonenumber-js for validation + formatting
- Use a UI library:
  - react-international-phone OR react-phone-number-input
- Do not hardcode +972 placeholders across the site. Centralize in one PhoneInput component.

Allowlist example:
["IL","AU","US","GB","FR","DE","ES","IT","NL","BE","CH","AT","SE","NO","DK","IE","CA","NZ"]

Backend:
- Validate phone is E.164
- Store:
  - phone_e164
  - phone_country
  - phone_national
- Twilio or Firebase phone auth must accept that E.164.

Important:
If you use Firebase Phone Auth, your sign-in page must accept +country code entry. No local-only input.

5) PASSKEYS (FACE ID / TOUCH ID) - REAL 2026 BIOMETRICS
Important reality:
Web does not directly “use Face ID” as a custom login method. The correct modern way is Passkeys (WebAuthn).
On iPhone/iPad, passkeys are backed by Face ID or Touch ID.

Implementation:
- Offer "Continue with Passkey" button if platform supports WebAuthn.
- Enrollment: after first successful login (Google/Apple/Phone), prompt:
  - "Secure your account with Passkey"
- Store credential ids in DB mapped to userId
- Use conditional UI:
  - If passkeys exist -> show passkey first
  - Fallback: Google/Apple/Phone

Security:
- For admin roles: require MFA even if passkey exists, or allow passkey as MFA if you treat it as phishing-resistant factor (recommended).
- Enforce step-up auth for high-risk actions (payout changes, KYC override, refunds).

6) EMAIL VERIFICATION AND PHONE VERIFICATION POLICY
You want “100% compliance”, but avoid blocking legitimate phone-only users.

Policy recommendation:
- If login method is phone-only: allow access, treat phoneVerified true
- If email exists: require emailVerified true for sensitive actions (wallet, provider, payouts)
- For providers: require at least one verified contact method AND verified identity docs.

Backend enforcement:
- Block non-GET on sensitive routes unless verified per policy.
- Never rely on frontend checks.

7) ADMIN AND MANAGEMENT ACCESS: APPROVAL WORKFLOW (NO SELF SERVICE)
Requirement:
Admin, management, staff must be approved by the company owner or a designated approver.

Do this:
- Add table access_requests:
  - id, user_id, requested_role, reason, status(pending/approved/denied), created_at, decided_by, decided_at
- When a user selects “staff/admin” intent:
  - Create access_request pending
  - Force redirect to /access-pending
  - Send notification to approver email with approve/deny links
- Approve endpoint:
  - requires super admin
  - sets role assignment
  - sets status active
  - logs audit event

Never allow “admin intent” to grant admin permissions automatically.

8) PROVIDER ONBOARDING: LIKE UBER / ROVER (DIFFERENT PIPELINE)
Provider flow stages:
1) Create account (auth)
2) Provider application form (services offered, coverage, availability)
3) Identity verification (ID + selfie)
4) Profile setup (public photo, bio, experience)
5) Compliance (terms, insurance declarations)
6) Review:

- Providers cannot accept jobs until stage == active

9) GOOGLE MAPS ADDRESS AUTOCOMPLETE RELIABILITY
Typical reasons suggestions do not appear:
- Places API not enabled
- Billing not enabled
- Referrer restrictions block the domain
- Script loaded with wrong language parameter or blocked by CSP
- iOS Safari blocks third-party script due to timing or mixed content

Best practice:
- Load Maps JS once globally, with dynamic language param based on UI language
- Use “fields” for place details, parse address components
- Save structured address:
  - formattedAddress, street, number, city, postalCode, countryCode, lat, lng

If you want maximum reliability:
- Use backend proxy for autocomplete and place details
- Frontend calls your endpoint, not Google directly
- This avoids exposing keys and avoids some browser restrictions

10) DATABASE IS SOURCE OF TRUTH, SHEETS IS OPTIONAL MIRROR
Answer:
Google Sheets is NOT a primary datastore for a platform like this.
It is fine as a mirror for operations, reporting, and quick viewing.

Correct architecture:
- Always write to Postgres first (transaction)
- Then enqueue a background job to append to Sheets
- Use idempotency key to avoid duplicates
- If Sheets fails, do not block signup or bookings
- Provide admin dashboard for “Sheets Sync Health”

Google Forms:
- Only acceptable for internal intake, not for core signup or onboarding
- Do not use Forms for provider onboarding or KYC
