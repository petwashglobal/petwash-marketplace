CORE PRINCIPLE
Location is not just a form field.
Location is a core marketplace input that must:
1. help the user enter address easily
2. store structured address and coordinates correctly
3. power nearest-provider matching
4. improve cost, speed, trust, and conversion
5. support fraud prevention and data integrity
6. stay reliable on iPhone, Android, desktop, and after browser / firmware updates

================================================================
1. ADDRESS / LOCATION INPUT RULE
================================================================

Every field such as:
- כתובת
- מיקום
- Location
- Search location
- Booking address
- Provider service area

must follow the same logic:

User types -> Google Places suggestions appear -> user selects -> UI shows human-readable address -> system stores structured location data internally

USER MUST SEE:
- readable address
- readable city / street / neighbourhood
- never raw coordinates

CORRECT DISPLAY:
"עוזי חיטמן 8 ראשון לציון ישראל"

WRONG DISPLAY:
"-37.8857, 145.0202"

CORRECT FRONTEND PRINCIPLE:
input.value = place.formatted_address

const locationData = {
  formattedAddress: place.formatted_address,
  lat: place.geometry.location.lat(),
  lng: place.geometry.location.lng(),
  placeId: place.place_id
}

CRITICAL RULE:
Display value and stored value must be separate.
Never overwrite visible address field with lat/lng.

================================================================
2. GPS BUTTON RULE
================================================================

The GPS / current-location button must never write raw coordinates into the visible input.

NEVER:
input.value = `${lat}, ${lng}`

ALWAYS:
input.value = "מיקום נוכחי"
or
input.value = "Current location"

Coordinates must stay internal only.

If reverse geocode fails:
- do not show coordinates
- keep lat/lng internally
- show current location label
- continue matching/search from stored coordinates

VERIFIED ROOT CAUSE THAT EXISTED:
The coordinate leak was caused by GPS fallback behavior, not by normal Google suggestion selection.

VERIFIED FIX:
The GPS fallback no longer shows raw coordinates in the visible field.

4. WHEN ONE FIELD IS ENOUGH VS WHEN EXTRA FIELDS ARE REQUIRED
================================================================

One smart Google address field is enough only if:
- user sees readable address
- system stores full coordinates and place components
- missing details can be completed separately where needed

Extra fields are needed in flows where operational fulfillment matters:
- apartment / unit
- floor
- entrance
- notes
- postal code where relevant

Browsing nearest providers can be simpler.
Actual booking, hosting, walker arrival, sitter arrival, transport, and service fulfillment often need richer address capture.

9. proximity tier labels were incomplete and could fall back to plain distance without clear context

8. WHAT IS NOW IMPLEMENTED
================================================================

VERIFIED COMMITS:
- 91e349dc
- a24548dc
- plus related fixes before these

A. PROXIMITY MATCHING ENGINE
Implemented server-side proximity logic using haversine distance and composite ranking.

Implemented:
1. haversineKm(lat1, lon1, lat2, lon2)
2. proximityScore(distanceKm)
3. compositeScore():
   - proximity 60%
   - rating 25%
   - trust 10%
   - volume 5%
4. proximityTier():
   - same_building
   - same_street
   - same_block
   - neighbourhood
   - same_city
   - metro_area
   - region
   - wider_area

B. SITTER / WALKER / STATION MATCHING
When lat/lng exist:
- fetch qualifying candidates
- compute haversine distance
- filter by radius
- rank by composite score
- paginate after ranking

When coordinates do not exist:
- graceful fallback to text-based search remains

Walkers:
- also respect provider's own serviceRadiusKm

Stations:
- use joined location coordinates for ranking

C. API RESPONSE NOW SUPPORTS
- distanceKm
- proximityTier
- matchScore

12. SERVER-SIDE COORDINATE VALIDATION
================================================================

This is now required and was fixed as a real security / integrity gap.

Server must reject:
- lat outside -90 to 90
- lng outside -180 to 180
- NaN values
- abuse radius outside allowed range

Radius should be clamped to safe bounds such as 1 to 200 km.

This prevents:
- malformed requests
- spoofed coordinates
- abuse of large search areas

15. SECURITY, FRAUD, DATA INTEGRITY
================================================================

Never trust client coordinates.

Always validate:
- lat
- lng
- radius

Required protections:
- rate limiting on auth, SMS, search, session creation
- abuse detection for spoofing and unrealistic jumps
- logging of location-driven search usage
- monitoring of suspicious repeated patterns

Fraud / abuse signals:
- malformed or fake coordinates
- repeated location spoofing
- abnormal rapid location jumps
- huge-radius scraping behavior
- mismatch between chosen area and later operational data
