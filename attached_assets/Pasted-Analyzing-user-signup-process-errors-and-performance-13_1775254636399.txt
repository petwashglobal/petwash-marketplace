PetWash Signup & Provider Registration — Full Bug Investigation

This covers every auth method (email, phone, Google, Apple, Facebook, Instagram, TikTok) and every registration path (new customers and providers), with exact file references.

PART 1 — NEW USER REGISTRATION (ALL METHODS)

Bug 1 — Email/password registration endpoint is dead (returns HTTP 410)

server/routes/auth.ts:76–85

POST /api/auth/register explicitly returns 410 Gone and does nothing else. The replacement is Firebase Auth + POST /api/users/create-profile. The problem is that the replacement flow has its own bugs (see below) and there is no clear client-side migration path guiding every signup surface to the new endpoint.

Bug 2 — Race condition in /api/users/create-profile creates duplicate loyalty records

server/routes.ts:11003–11010

Two simultaneous requests for the same Firebase UID (e.g., user double-taps the submit button) both try to insert the same user. The duplicate key error is caught and silently continues — but both requests then proceed to call assignCustomerMembership(), which has no ON CONFLICT guard. Result: two loyalty profile rows for one user, corrupted points balance from day one.

Bug 3 — Email/social auth users never get a wallet or loyalty profile created

server/routes.ts:10856–11111 vs server/routes/publicAuthRoutes.ts:560–596

Phone OTP users get wallet + loyalty profile created at verification time. Email and all social OAuth users (Google, Apple, Facebook, Instagram, TikTok) go through POST /api/users/create-profile which does neither. Any page that queries wallet balance or loyalty tier for an email/social-auth user will get null or crash. The inconsistency is structural — there is no shared "post-registration setup" function called by all auth paths.

Bug 4 — Phone OTP flow never collects name or email, then blocks profile completion

server/routes/publicAuthRoutes.ts:976–1015 and server/routes/post-login.ts:27–39, 779–801

After phone OTP verification the user has:

✓ Firebase auth
✓ users.phone populated
✗ firstName = null, lastName = null, email = null
The system then sends them to /complete-profile. But POST /api/auth/post-login at line 779–781 returns 400 NAME_REQUIRED if firstName or lastName is empty. The phone signup flow never asked for these fields. The user is in a dead end: they authenticated successfully but cannot proceed anywhere.

Bug 5 — /verify-email redirect destination does not exist

server/routes/post-login.ts:291–301 and client/src/pages/SignIn.tsx:159–214

Email-auth users who haven't verified their address are told to go to /verify-email. The client navigates there. There is no /verify-email page in the client router and no API endpoint to send or confirm verification emails. Users land on a blank page or 404 with no way out.

Bug 6 — Four independent user-creation endpoints with no coordination

server/routes.ts:10856, server/routes/publicAuthRoutes.ts:504, publicAuthRoutes.ts:943, server/routes/user-profile.ts:229

Four separate code paths can each independently INSERT a row into the users table:

POST /api/users/create-profile — main flow for Firebase/email
POST /api/auth/phone-session — creates Firebase user on phone lookup
POST /api/auth/phone/otp/verify — creates PostgreSQL user row after verification
PATCH /api/user/profile — will INSERT if user row is missing
Only paths 1 and 3 create wallets; only path 3 creates loyalty profiles; none of them coordinate. Each has different field requirements and triggers different side effects.

Bug 7 — Firebase-to-PostgreSQL sync is fire-and-forget, not awaited

server/routes.ts:1088–1150

When a user first authenticates via any Firebase provider, the route calls authService.ensureUserInPostgres() inside an (async () => { ... })() IIFE that is not awaited before the 200 OK response is sent to the client. The client receives a successful session and immediately calls POST /api/auth/post-login. At that point the PostgreSQL row may not exist yet. The post-login handler catches this and tries a recovery upsert, but if that also races or fails, the user gets a 404 USER_NOT_FOUND error on their very first navigation after sign-in.

Bug 8 — Post-login return URL is lost after profile completion

client/src/pages/CompleteProfile.tsx:188–200

If a user is mid-booking and gets redirected to /complete-profile?from=/booking/123, the ?from= parameter is never read or passed forward. After profile completion the server decides the redirect destination (e.g., /home). The booking-in-progress is silently abandoned.

PART 2 — SOCIAL OAUTH (GOOGLE, APPLE, FACEBOOK, INSTAGRAM, TIKTOK)

Bug 9 — Facebook OAuth callback does not exist on the server

server/routes/social-oauth.ts (entire file)

Instagram and TikTok have full OAuth callback routes (lines 79–176 and 178–269 respectively). Facebook has zero server-side implementation. The client can trigger Firebase's FacebookAuthProvider flow, but when Firebase completes the auth there is no /api/auth/social/facebook/callback or equivalent. Firebase creates the user in its system; the PostgreSQL row is never created; the wallet is never created. A Facebook user is Firebase-authenticated but completely invisible to the application database.

Bug 10 — Instagram and TikTok OAuth callbacks create a Firebase user but not a PostgreSQL user

server/routes/social-oauth.ts:137–158 (TikTok) and 232–251 (Instagram)

Both callbacks call adminAuth.createUser(...) in Firebase and issue a custom token, then redirect to /signin?oauthCode=.... There is no INSERT into the users PostgreSQL table. The user claims their custom token, Firebase auth succeeds, and then every server API call that queries users WHERE id = 'tiktok:xxx' returns nothing.

The root cause: AuthService.ensureUserInPostgres() at line 231–233 returns null and does not create the row when email is null. Both TikTok and Instagram can return null emails for users who have not disclosed their email.

Bug 11 — Apple Sign-In: returning users lose their profile on second login

server/routes/post-login.ts:198 and server/services/AuthService.ts:231–233

Apple only sends the user's email on the first sign-in ever. On every subsequent sign-in the email field is absent from Apple's response. The PostgreSQL row for the user already exists (from the first login), but ensureUserInPostgres is called again on each login and receives email = undefined. Because the function returns null when email is missing, it fails silently instead of looking up the existing row by Firebase UID. If the session was created in a fresh environment (new device, cleared cookies), the user effectively cannot be found and gets 404 USER_NOT_FOUND.

Bug 12 — Google OAuth: missing GOOGLE_WEB_CLIENT_SECRET causes a 500 error with no clear message

server/routes/mobile-auth.ts:11–12, 41

GOOGLE_WEB_CLIENT_SECRET has no fallback. If it is unset the client variable is null and the endpoint throws a generic 500 error when called. The environment variable MOBILE_LINK_SECRET (used as JWT secret in this route, line 13) is different from JWT_SECRET used everywhere else. If MOBILE_LINK_SECRET is unset, the JWT token is silently skipped at line 174 — the client may expect a token in the response and breaks without one.

Bug 13 — COOKIE_SECRET missing in production crashes the entire server at startup

server/routes/social-oauth.ts:12–17

TypeScript
process.env.COOKIE_SECRET ?? (() => {
  if (NODE_ENV === 'production') throw Error('COOKIE_SECRET must be set in production');
  return 'dev-only-...';
})()
If COOKIE_SECRET is not in the production environment, the module throws synchronously during route registration, and the entire Express server fails to start. All signup flows — not just TikTok/Instagram — go down.

Bug 14 — Social OAuth users have no wallet (except Google via mobile-auth.ts)

server/routes/mobile-auth.ts:134–146 vs. server/routes/social-oauth.ts (entire file)

mobile-auth.ts auto-creates a wallet for Google users. Nothing in social-oauth.ts does the same for Instagram, TikTok, or Facebook. And Apple Sign-In (Firebase-only flow, no dedicated server callback) also never creates a wallet. All non-Google social users cannot use wallet balance, credits, or loyalty points.

Bug 15 — OAuth intent lost after redirect: "Become Provider" via Google goes to /home

client/src/pages/SignIn.tsx:158–196, 217–223

When a user selects "Become Provider" and then clicks "Google Sign-In":

The intent is stored in localStorage.
Google OAuth redirects away and back.
handleOAuthCustomToken() completes the sign-in.
It calls navigate(customRedirect) or navigatePostLogin() — neither reads the stored intent.
The user ends up at /home instead of /provider-onboarding. The provider signup path via any OAuth method is silently broken.

Bug 16 — Safari ITP loses the OAuth redirect marker

client/src/pages/SignIn.tsx:56–90, 509–588

On cross-domain OAuth redirects (Firebase → petwash.co.il), Safari's Intelligent Tracking Prevention can clear localStorage between the redirect and the return. The redirect marker that tracks which provider the user chose and what they were doing is lost. The code at line 525 has a partial mitigation but the fallback just silently goes to /home. Users on iOS Safari who try OAuth see the login succeed but get dropped with no context.

Bug 17 — OAuth redirect result consumed by two competing handlers

client/src/pages/SignIn.tsx:509–588 and client/src/contexts/AuthProvider.tsx

Both AuthProvider.tsx (on mount) and SignIn.tsx call getRedirectResult(). Firebase clears the result after the first read. Whichever reads second gets null. The second reader shows an error toast "Sign-in not completed" even though the sign-in succeeded. Users see a confusing error message on successful login.

Bug 18 — Account linking fails silently

client/src/pages/SignIn.tsx:1499–1520

When linking a social credential to an existing account, the linkWithCredential() call is inside a try/catch that only logs a warning and clears the pendingOAuthCredential state regardless of success or failure. Users believe they linked their Google account but did not. The next time they try Google login they get "account already exists with this email" again with no explanation.

PART 3 — PROVIDER REGISTRATION

Bug 19 — Provider KYC exception creates a permanent deadlock

server/routes/provider-onboarding.ts:1086–1131

If the async KYC2026 verification step throws an unhandled exception, the rescue handler at line 1087 tries to set status to pending_review. But if the row has already been updated away from processing, the SQL WHERE status = 'processing' matches zero rows. The status never moves, the provider is stuck forever in processing, and there is no admin tool or cron job to recover them.

Bug 20 — Provider bank accounts stored in plaintext when encryption key is missing or short

server/routes/contractor-onboarding.ts:32–44

TypeScript
if (!masterKey || masterKey.length < 32) {
  logger.warn('[...] DOCUMENT_ENCRYPTION_KEY not set — bank account stored unencrypted');
  return plaintext;  // IBAN written to DB in plaintext
}
The encryption silently falls back to plaintext instead of failing hard. If DOCUMENT_ENCRYPTION_KEY is absent or less than 32 bytes in any environment, all IBAN numbers are stored in the clear. This is a PCI and Israeli Privacy Protection Law violation.

Bug 21 — Background check endpoint stores a record but runs no actual check

server/routes/contractor-onboarding.ts:277–320

TypeScript
result: backgroundCheck.result || "PENDING"
The "Submit Background Check" step saves the request to the database with status PENDING and never calls any external service. The contractor is given a certificate record immediately. No criminal background screening is ever performed.

Bug 22 — Police check not required before provider activation (Israeli law compliance)

server/routes/provider-onboarding.ts and server/routes/police-check.ts

Israeli law (תעודת יושר) requires a police clearance certificate before a service provider can work with animals or children. The police-check.ts route exists as a standalone flow but is not enforced as a required step in provider-onboarding.ts or provider-applications.ts. Providers can reach approved status without submitting one.

Bug 23 — No rejection email sent to declined providers

server/routes/provider-applications.ts:1235

TypeScript
// TODO: Send rejection email
When an admin rejects a provider application, the provider receives no notification whatsoever. The comment acknowledges this but the implementation is missing.

Bug 24 — Multiple disconnected provider tables with no foreign keys between them

shared/schema.ts:3996, 4562, 6915, 7815, 9705, 11805

There are six separate tables for different types of providers: sitterProfiles, walkerProfiles, trainers, providers, contractors, and octopusProviders. Only sitterProfiles has a proper FK to users.id. The others reference userId as a plain varchar with no constraint. A user can have a row in all six tables with no relation between them. An admin who approves a walker profile does not affect the trainer profile. An admin query for "all active providers" must union six tables and there is no guarantee the data is consistent.

Bug 25 — Walk My Pet and Academy provider registration require no verification

server/routes/walk-my-pet.ts:48–102, server/routes/academy.ts:575

POST /api/walk-my-pet/walkers/register and the trainer registration equivalent create provider profiles immediately with no document upload, no KYC, no background check, no police clearance check. Any authenticated user can self-register as a professional dog walker or trainer and begin appearing in search results with isActive: true.

Bug 26 — Provider public stats endpoint has no authentication

server/routes/provider-intake.ts:64

GET /api/provider-intake/stats returns counts of pending, approved, and rejected applications. No auth middleware is applied. Any unauthenticated request returns this internal management data.

PART 4 — CLIENT-SIDE REGISTRATION BUGS

Bug 27 — Social OAuth users never call /api/customer/register

client/src/pages/SignIn.tsx:963–984

After OAuth completes, the client only calls /api/loyalty/auto-enroll. Email users who sign up via CustomerSignupModal.tsx call the full /api/customer/register endpoint. The two paths create different levels of completeness in the database. Social auth users are missing customer profile data that the system expects to exist.

Bug 28 — Phone verification claim not refreshed in Firebase token

client/src/pages/ProviderOnboarding.tsx:128–154

After OTP verification the client sets phoneVerified = true in local component state. The Firebase ID token is never refreshed (getIdToken(true) is never called). Backend APIs that verify the phone_verified claim in the Firebase token reject requests with 403 even though the UI shows a green checkmark.

Bug 29 — Provider onboarding redirect loop when auth state is loading

client/src/pages/ProviderOnboarding.tsx:40–45

TypeScript
useEffect(() => {
  if (user === null) {
    navigate('/signin?redirect=/provider-onboarding');
  }
}, [user, navigate]);
During the initial Firebase auth state resolution, user is null before the SDK has finished loading. This fires the redirect immediately, sends the user to /signin, and they loop back again. The guard should be if (user === null && !isLoading).

Bug 30 — Sign-in has 7 sequential API round-trips (3–5 second delay)

client/src/pages/SignIn.tsx:1459–1600

reCAPTCHA → Firebase sign-in → ID token fetch → server session create → session verify → loyalty auto-enroll → analytics — each call waits for the previous one to finish. On a mobile network this produces a visible 3–5 second delay after the user submits their credentials. Loyalty and analytics calls do not need to block navigation and could be deferred.

The 5 fixes that unblock the most users immediately

Add ?from= preservation and wallet+loyalty creation to ALL auth paths — a single registerUserInPostgres(uid, provider) helper called from every auth completion point would fix Bugs 3, 9, 10, 11, 14, 27 in one change.
Phone OTP flow must collect firstName + lastName + email before issuing the token, or /complete-profile must allow saving without them — fixes Bug 4, 6, 7.
Create the /verify-email page and the resend-verification endpoint — fixes Bug 5, unblocks all email signups.
Add Facebook server-side OAuth callback mirroring the TikTok/Instagram pattern in social-oauth.ts — fixes Bug 9.
Guard provider onboarding redirect with !isLoading and refresh Firebase token after phone OTP — fixes Bugs 28, 29, relieves the provider signup loop.
