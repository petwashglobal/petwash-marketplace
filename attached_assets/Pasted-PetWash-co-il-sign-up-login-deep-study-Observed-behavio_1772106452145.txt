PetWash.co.il sign‑up & login deep study

Observed behaviour

Website structure and sign‑in options
	•	The PetWash site is a single‑page application hosted on petwash.co.il.
	•	When visiting the site there is a cookie banner; after accepting, the site displays a sign‑in dialog.
	•	The sign‑in dialog lets users pick a role (booker, club member, service provider, or staff).  Each role opens a list of authentication providers: Google (Gmail), Apple, Facebook, TikTok, Instagram and a phone‑/SMS‑based login.
	•	When selecting Become a service provider, the site calls signInWithRedirect() from the Firebase JS SDK.  This redirects the browser to Google or another provider and expects to store state in a cross‑origin iframe hosted at signinpetwash.firebaseapp.com.

Issues reproducing
	•	On desktop Chrome under default settings, clicking Gmail opens a Google account chooser, but the user must complete the login.  We could not finish the Google flow due to lack of credentials, but users report that after logging in the page spins indefinitely and eventually shows a red error.
	•	On mobile (iOS/Safari and Chrome for Android), users report that new sign‑ups as a provider do not complete—after SMS verification or Google login they are not redirected to the next step, leaving the page stuck.
	•	Phone‑based verification (SMS) works; the OTP is delivered and accepted, but the app does not proceed to the provider‑on‑boarding route.  Other roles (booking, club membership) complete successfully.

Crash and performance fix

The project previously had a crash due to two services (OctopusBrainService.ts and ProductionWebsiteMonitorService.ts) starting health scans during development.  These scans invoked Gemini AI calls and internal/external HTTP checks 5–8 seconds after import, overlapping with Vite’s TypeScript compilation.  This saturated the single‑threaded Node process and caused a crash every 14.8 s.  The services now start only when NODE_ENV=production.  The crash is resolved.

Root causes for current sign‑up/login issues

Google/OAuth logins spin indefinitely

From June 2024 onwards Chrome (v115+), Safari (16.1+) and Firefox (109+) block third‑party cookies by default.  Firebase’s signInWithRedirect() relies on a cross‑origin iframe hosted on firebaseapp.com to store state during the redirect.  When third‑party storage is blocked, the helper iframe cannot save the state, and the app never receives a valid redirect result.  The Firebase documentation warns that redirect sign‑ins will break on these browsers unless applications adopt one of several mitigation options ￼.  PetWash currently hosts its app on petwash.co.il but still uses the default signinpetwash.firebaseapp.com as the authDomain, so third‑party cookies are blocked.

Provider sign‑up not completing after SMS verification
	•	For SMS/phone logins, Firebase returns a UserCredential as soon as the OTP is verified.  The application must then create/update a provider profile in Firestore and redirect to the provider on‑boarding route (e.g. /provider/onboarding).  In the current implementation the onAuthStateChanged handler only watches for logged‑in customers and redirects them to /app/home, leaving providers stuck on the login page.
	•	There is no conditional logic that detects a new provider user (additionalUserInfo.isNewUser) and triggers the provider registration flow.  The route for provider onboarding may be missing or not defined in the router, causing a 404 or silent failure.
	•	On mobile browsers the router may fail due to a path mismatch (e.g. /#/provider/welcome vs /provider/welcome) or due to the use of relative URLs.  Without a defined route, the SPA remains on the login page.
