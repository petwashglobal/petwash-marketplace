PHASE 4.5 - BUSINESS SURVIVAL HARDENING

GOAL
Make the platform safe under real-world conditions:
- prevent catastrophic mistakes
- survive partial failures
- enforce strict permissions
- guarantee financial integrity
- provide instant shutdown and fallback paths

This phase is NOT about features.
It is about protecting the business.

LOCKED PRINCIPLES
- no silent failures
- all critical actions must be reversible or guarded
- every financial mutation must be idempotent
- every automated system must have a kill switch
- permissions must be explicit and enforced at route level
- all exports and sensitive data must be access-controlled
- system must degrade safely, not break

==================================================
4.5A - PERMISSION HARDENING & ACCESS CONTROL
==================================================

GOAL
Ensure every endpoint enforces correct role + capability.

DB
Extend finance_role_capabilities if needed:
- enforce explicit mapping per endpoint group

BACKEND
- Audit all /admin/wallet/* routes
- Add requireFinanceRole(role) OR capability check to:
  - payouts
  - refunds
  - approvals
  - replay
  - archive execution
  - policy changes

Add:
- GET /admin/wallet/permission-audit
Returns:
- endpoint → required role
- missing guards (if any)

FRONTEND
Governance tab
- “Permission Audit” card
- list of critical endpoints and their role requirements

ACCEPTANCE
- no admin endpoint without guard
- read/write/admin separation enforced
- audit returns zero unprotected endpoints

==================================================
4.5B - MONEY FLOW INTEGRITY CHECKS
==================================================

GOAL
Guarantee correctness of all financial flows.

COVER FLOWS
- booking → hold → release
- refund → approval → execution
- payout → batch → reconciliation → settlement
- clawback → negative payout handling

DB
Create table: money_flow_checks
- id SERIAL
- check_type VARCHAR(64)
- entity_id VARCHAR(128)
- expected_value NUMERIC
- actual_value NUMERIC
- status VARCHAR(16)
- created_at TIMESTAMPTZ DEFAULT NOW()

BACKEND
- POST /admin/wallet/run-money-checks
- GET /admin/wallet/money-check-results

Checks:
- batch total = sum(entries)
- settled = reconciled entries
- refunds ≤ debits
- no negative wallet states (unless allowed)

FRONTEND
Command Center
- “Money Integrity” panel
- pass/fail indicators

ACCEPTANCE
- all checks deterministic
- failures clearly identify root entity
- no silent mismatch

==================================================
4.5C - GLOBAL KILL SWITCHES
==================================================

GOAL
Allow immediate shutdown of critical operations.

DB
Create table: system_kill_switches
- key VARCHAR(64) PRIMARY KEY
- enabled BOOLEAN
- updated_at TIMESTAMPTZ

Seed:
- payouts_enabled
- remittances_enabled
- automation_enabled
- policy_execution_enabled
- assistant_execution_enabled

BACKEND
- GET /admin/wallet/kill-switches
- POST /admin/wallet/kill-switches/:key/toggle

Enforce checks in:
- payout batch creation
- remittance sending
- automation jobs
- assistant execution endpoints

FRONTEND
Control Center
- “Kill Switches” panel (toggle UI)

ACCEPTANCE
- disabling a switch blocks execution instantly
- system returns controlled error, not crash

==================================================
4.5D - FAILURE RECOVERY & RETRY SAFETY
==================================================

GOAL
Ensure retries do not corrupt data.

REQUIREMENTS
- all financial endpoints must be idempotent
- duplicate requests must not duplicate effects

DB
Create table: idempotency_keys
- key VARCHAR(128) PRIMARY KEY
- endpoint VARCHAR(128)
- response_hash TEXT
- created_at TIMESTAMPTZ

BACKEND
- Wrap critical endpoints:
  - payouts
  - refunds
  - approvals
  - replay
with idempotency guard

- POST /admin/wallet/test-retry-safety

FRONTEND
No UI required (internal tool)

ACCEPTANCE
- duplicate request returns same result
- no duplicate financial entries created

==================================================
4.5E - SECURITY HARDENING
==================================================

GOAL
Protect sensitive data and endpoints.

BACKEND
- validate all file uploads (CSV, archive, replay)
- enforce file size + type limits
- sanitize all input fields

- restrict:
  - export endpoints
  - audit logs
  - governance packs
to finance roles only

Add:
- GET /admin/wallet/security-audit
Returns:
- open risks
- endpoints missing validation

FRONTEND
Governance tab
- “Security Audit” panel

ACCEPTANCE
- no public access to sensitive endpoints
- uploads validated
- audit shows zero critical risks

==================================================
4.5F - CROSS-PLATFORM CONSISTENCY CHECK
==================================================

GOAL
Ensure system states match across all surfaces.

CHECKS
- provider vs admin payout status
- booking vs wallet vs payout linkage
- dispute state vs outcome vs refund
- reconciliation vs settlement

BACKEND
- GET /admin/wallet/consistency-check

Returns:
- mismatched entities
- count per type
- sample IDs

FRONTEND
Command Center
- “Consistency Check” panel

ACCEPTANCE
- mismatches are traceable
- zero state clearly shown

==================================================
4.5G - GO-LIVE CHECKLIST & ROLLBACK RUNBOOK
==================================================

GOAL
Provide a controlled launch and recovery plan.

DB
Create table: go_live_checklist
- id SERIAL
- item VARCHAR(128)
- status VARCHAR(16)
- verified_by VARCHAR(128)
- verified_at TIMESTAMPTZ

Seed items:
- permissions verified
- money flows verified
- kill switches tested
- alerts working
- backups confirmed

BACKEND
- GET /admin/wallet/go-live-checklist
- POST /admin/wallet/go-live-checklist/:id/verify

Add:
- GET /admin/wallet/rollback-plan
(static JSON instructions)

FRONTEND
Governance
- “Go Live Checklist” card
- verification toggles
- rollback plan viewer

ACCEPTANCE
- all checklist items must be verified before launch
- rollback plan always accessible
