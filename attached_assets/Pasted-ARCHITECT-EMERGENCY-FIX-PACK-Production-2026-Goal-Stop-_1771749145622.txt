1) THE "OFFLINE" / 503 RED BOX IS NOT YOUR INTERNET
======================================================================
Symptom:
- UI shows: error:"offline" ... 503 while you are clearly online.

Root cause (most common in Firebase Hosting + Cloud Run):
- Frontend is calling /api/... on petwash.co.il (Firebase Hosting static)
- Firebase Hosting is NOT routing /api to Cloud Run (or base URL env var is missing)
- So calls hit the wrong place and return 503 -> your UI translates it to "offline"

Immediate fix (choose ONE, do not mix):
A) REWRITE /api TO CLOUD RUN IN firebase.json (best, simplest)
- In Firebase Hosting config, add rewrites:

firebase.json (example)
{
  "hosting": {
    "public": "dist",
    "ignore": ["firebase.json", "**/.*", "**/node_modules/**"],
    "rewrites": [
      { "source": "/api/**", "run": { "serviceId": "petwash-backend", "region": "me-west1" } },
      { "source": "**", "destination": "/index.html" }
    ]
  }
}

Notes:
- serviceId must match your Cloud Run service name
- region must match where Cloud Run is deployed

B) USE VITE_PRODUCTION_API_URL (works but easier to break)
- All frontend API calls must use:
  `${import.meta.env.VITE_PRODUCTION_API_URL}/api/...`
- On Firebase build/deploy you MUST set:
  VITE_PRODUCTION_API_URL=https://YOUR-CLOUD-RUN-URL

If you do B, confirm the deployed build actually contains the env value (Firebase builds often miss it).

How to find your Cloud Run backend URL (you do NOT need to guess):
- Google Cloud Console -> Cloud Run -> click your service -> "URL" at the top
or CLI:
gcloud run services describe petwash-backend --region me-west1 --format="value(status.url)"

Production smoke test (must return 200):
- Open in browser:
https://YOUR-CLOUD-RUN-URL/api/health
- Also test from Hosting:
https://petwash.co.il/api/health
If /api rewrite is correct, both should succeed.

UI FIX (stop calling it offline):
- Do NOT label 503 as offline.
- If response status is 401/403 -> "Not authorized"
- If 429 -> "Too many attempts, try later"
- If 502/503/504 -> "Service temporarily unavailable"
- Only show "offline" when navigator.onLine is false OR fetch throws TypeError network failure.

2) ADDRESS AUTOCOMPLETE NOT WORKING (GOOGLE PLACES)
======================================================================
Your screenshot shows:
"Address suggestions temporarily unavailable. You can type your address manually."
That means Google Places is failing and your fallback is showing. Good fallback, but we must fix the cause.

There are only 5 real causes in production:
1) VITE_GOOGLE_MAPS_API_KEY missing in the deployed build
2) Maps JavaScript API or Places API not enabled
3) Billing not enabled on the Google Cloud project
4) HTTP referrer restrictions missing petwash.co.il
5) Backend proxy key missing/blocked (if you use /api/google/places-* endpoints)

Fix checklist (do all):
A) Google Cloud Console -> APIs
- Enable: "Maps JavaScript API"
- Enable: "Places API"

B) Billing
- Make sure billing is enabled for that Google Cloud project

C) API key restrictions (MOST COMMON)
- Credentials -> your browser key
- Application restrictions: HTTP referrers
Add:
https://petwash.co.il/*
https://www.petwash.co.il/*
(also add your Firebase preview domains if you use them)

D) If using backend proxy endpoints
- Cloud Run env must include GOOGLE_MAPS_API_KEY
- Confirm proxy endpoints return 200:
https://YOUR-CLOUD-RUN-URL/api/google/places-autocomplete?input=ramat
If this fails, fix Cloud Run env var or key restrictions.

Production UX rule:
- If autocomplete fails, do not show scary error text.
- Show: "Type address manually" + small info icon "Autocomplete unavailable right now."

4) SMS SENDER NAME (WHY YOU SEE A NUMBER)
======================================================================
Reality:
- In many countries the sender shows a phone number by default.
- A "name" sender requires either:
  - Alphanumeric sender ID support in that country, or
  - A registered branded sender / messaging service setup, or
  - Regulatory registration (varies by country)

What you can do NOW so it always looks branded:
A) Always include brand name in the message body first line:
"PetWash: Your verification code is 123456"

B) Use a Twilio Messaging Service
- Create Messaging Service in Twilio
- Add your phone number to it
- Set it in backend: TWILIO_MESSAGING_SERVICE_SID
This improves deliverability and management.

C) For Israel specifically
- Often you will still see a number.
- That is normal for many routes.
- Brand name in the message content is the reliable solution.

Better OTP SMS template (best for iOS/Android autofill):
PetWash: 123456
Do not share this code.
Expires in 5 minutes.

Hebrew:
PetWash: 123456
לא לשתף את הקוד.
הקוד בתוקף ל-5 דקות.

6) WHO GOES WHERE AFTER SIGNUP (THE WIRING LOGIC)
======================================================================
You are correct: customer, provider, and staff cannot share the same onboarding path.

Server must decide next step, not client:
POST /api/auth/post-login -> returns:
{
  "nextPath": "/complete-profile",
  "requiredActions": ["complete_profile","accept_terms"]
}

Routing rules:
- Public customer -> complete basic profile (name, phone optional, address optional) -> can use services
- Loyalty member -> full profile + DOB (if required) + consents -> loyalty dashboard
- Provider applicant -> complete profile + provider application + background checks/ID -> status page until approved
- Staff/admin -> must request access -> admin approval required -> MFA required -> control panel

Absolutely never allow "admin" role via signup intent.
