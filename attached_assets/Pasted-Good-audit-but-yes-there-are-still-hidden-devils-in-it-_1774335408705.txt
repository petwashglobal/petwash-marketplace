Good audit, but yes, there are still hidden devils in it.

The biggest ones are these:
	1.	Fail-open CAPTCHA is dangerous
If RECAPTCHA_SECRET_KEY is missing or Enterprise verification fails badly, the flow can still pass. That means your phone OTP protection may look “working” while actually allowing unverified traffic. This is a real security hole, not a cosmetic issue.
	2.	Two backend CAPTCHA verifiers is a design bug
You have server/lib/verifyCaptcha.ts and server/routes/recaptcha.ts doing almost the same job with slightly different behavior. That creates drift, inconsistent thresholds, inconsistent logs, and future bugs. There should be one canonical verification service only.
	3.	Session split-brain risk
Client can be logged into Firebase, but backend session cookie can fail to write. Then the UI looks signed in but all protected API calls fail with 401. That is a nasty hidden bug because the user thinks login succeeded. You need a hard post-login validation step: if /api/auth/session fails, immediately sign out the Firebase client and show a real error.
	4.	iPhone redirect path has race risk
Two redirect/session-related useEffect chains in SignIn.tsx is fragile. On Safari this can cause null redirect results, duplicate handling, or partial state restore. Redirect resolution should happen in one place only.
	5.	iPad detection logic is too clever
isIOS() then isIPhone() is overcomplicated. It may work now, but it is brittle across iPadOS changes. You want one explicit auth strategy resolver, not layered device guesses.
	6.	Popup blocker risk still exists
If anything async sneaks in before signInWithPopup(), Safari may block it. This must stay directly inside the user gesture path. Developer should audit that no analytics, toasts, logging, or async helper gets inserted before popup launch.
	7.	Phone verify step is weaker than phone send step
send-code is CAPTCHA protected. verify-code is only rate-limited. That is uneven defense. It may be acceptable, but it should be a conscious choice, not an accident.
	8.	Admin visibility is weak
Failed CAPTCHA and failed auth attempts are still too hidden. Logs only is not enough. Octopus admin should show:

	•	failed phone CAPTCHA
	•	failed OTP verify
	•	failed OAuth callback
	•	failed session cookie creation
	•	provider signup rejected by CAPTCHA

	9.	App Check disabled
Not necessarily today’s login bug, but still a real gap. If you rely heavily on Firebase resources, leaving App Check off reduces protection.
	10.	Google / Apple OAuth have zero CAPTCHA
That is normal, but it means your real protection there is:

	•	CSP
	•	authorized domains
	•	Firebase config
	•	session handling
	•	rate limits
The team must not keep talking about reCAPTCHA as if it protects Google sign-in. It does not.

	11.	Provider flow can partially succeed
If provider application is created but auth session fails, you get database state without user state. That must be handled cleanly with recovery UX.
	12.	Octopus integration is not fully observable
The audit says auth flows feed Octopus through /api/auth/session and /api/auth/post-login, but it still sounds too implicit. You need one explicit trace for every auth path:

	•	method
	•	Firebase result
	•	session cookie write
	•	Octopus user lookup
	•	final route
	•	failure reason if broken
