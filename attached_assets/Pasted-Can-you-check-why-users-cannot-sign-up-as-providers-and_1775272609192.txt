PetWash Signup & Provider Registration — Full Bug Investigation

This covers every auth method (email, phone, Google, Apple, Facebook, Instagram, TikTok) and every registration path (new customers and providers), with exact file references.

PART 1 — NEW USER REGISTRATION (ALL METHODS)

Bug 1 — Email/password registration endpoint is dead (returns HTTP 410)

server/routes/auth.ts:76–85

POST /api/auth/register explicitly returns 410 Gone and does nothing else. The replacement is Firebase Auth + POST /api/users/create-profile. The problem is that the replacement flow has its own bugs (see below) and there is no clear client-side migration path guiding every signup surface to the new endpoint.

Bug 2 — Race condition in /api/users/create-profile creates duplicate loyalty records

server/routes.ts:11003–11010

Two simultaneous requests for the same Firebase UID (e.g., user double-taps the submit button) both try to insert the same user. The duplicate key error is caught and silently continues — but both requests then proceed to call assignCustomerMembership(), which has no ON CONFLICT guard. Result: two loyalty profile rows for one user, corrupted points balance from day one.

Bug 3 — Email/social auth users never get a wallet or loyalty profile created

server/routes.ts:10856–11111 vs server/routes/publicAuthRoutes.ts:560–596

Phone OTP users get wallet + loyalty profile created at verification time. Email and all social OAuth users (Google, Apple, Facebook, Instagram, TikTok) go through POST /api/users/create-profile which does neither. Any page that queries wallet balance or loyalty tier for an email/social-auth user will get null or crash. The inconsistency is structural — there is no shared "post-registration setup" function called by all auth paths.

Bug 4 — Phone OTP flow never collects name or email, then blocks profile completion

server/routes/publicAuthRoutes.ts:976–1015 and server/routes/post-login.ts:27–39, 779–801

After phone OTP verification the user has:

✓ Firebase auth
✓ users.phone populated
✗ firstName = null, lastName = null, email = null
The system then sends them to /complete-profile. But POST /api/auth/post-login at line 779–781 returns 400 NAME_REQUIRED if firstName or lastName is empty. The phone signup flow never asked for these fields. The user is in a dead end: they authenticated successfully but cannot proceed anywhere.

Bug 5 — /verify-email redirect destination does not exist

server/routes/post-login.ts:291–301 and client/src/pages/SignIn.tsx:159–214

Email-auth users who haven't verified their address are told to go to /verify-email. The client navigates there. There is no /verify-email page in the client router and no API endpoint to send or confirm verification emails. Users land on a blank page or 404 with no way out.

Bug 6 — Four independent user-creation endpoints with no coordination

server/routes.ts:10856, server/routes/publicAuthRoutes.ts:504, publicAuthRoutes.ts:943, server/routes/user-profile.ts:229

Four separate code paths can each independently INSERT a row into the users table:

POST /api/users/create-profile — main flow for Firebase/email
POST /api/auth/phone-session — creates Firebase user on phone lookup
POST /api/auth/phone/otp/verify — creates PostgreSQL user row after verification
PATCH /api/user/profile — will INSERT if user row is missing
Only paths 1 and 3 create wallets; only path 3 creates loyalty profiles; none of them coordinate. Each has different field requirements and triggers different side effects.

Bug 7 — Firebase-to-PostgreSQL sync is fire-and-forget, not awaited

server/routes.ts:1088–1150

When a user first authenticates via any Firebase provider, the route calls authService.ensureUserInPostgres() inside an (async () => { ... })() IIFE that is not awaited before the 200 OK response is sent to the client. The client receives a successful session and immediately calls POST /api/auth/post-login. At that point the PostgreSQL row may not exist yet. The post-login handler catches this and tries a recovery upsert, but if that also races or fails, the user gets a 404 USER_NOT_FOUND error on their very first navigation after sign-in.

Bug 8 — Post-login return URL is lost after profile completion

client/src/pages/CompleteProfile.tsx:188–200

If a user is mid-booking and gets redirected to /complete-profile?from=/booking/123, the ?from= parameter is never read or passed forward. After profile completion the server decides the redirect destination (e.g., /home). The booking-in-progress is silently abandoned.

PART 2 — SOCIAL OAUTH (GOOGLE, APPLE, FACEBOOK, INSTAGRAM, TIKTOK)

Bug 9 — Facebook OAuth callback does not exist on the server

server/routes/social-oauth.ts (entire file)

Instagram and TikTok have full OAuth callback routes (lines 79–176 and 178–269 respectively). Facebook has zero server-side implementation. The client can trigger Firebase's FacebookAuthProvider flow, but when Firebase completes the auth there is no /api/auth/social/facebook/callback or equivalent. Firebase creates the user in its system; the PostgreSQL row is never created; the wallet is never created. A Facebook user is Firebase-authenticated but completely invisible to the application database.

Bug 10 — Instagram and TikTok OAuth callbacks create a Firebase user but not a PostgreSQL user

server/routes/social-oauth.ts:137–158 (TikTok) and 232–251 (Instagram)

Both callbacks call adminAuth.createUser(...) in Firebase and issue a custom token, then redirect to /signin?oauthCode=.... There is no INSERT into the users PostgreSQL table. The user claims their custom token, Firebase auth succeeds, and then every server API call that queries users WHERE id = 'tiktok:xxx' returns nothing.

The root cause: AuthService.ensureUserInPostgres() at line 231–233 returns null and does not create the row when email is null. Both TikTok and Instagram can return null emails for users who have not disclosed their email.

Bug 11 — Apple Sign-In: returning users lose their profile on second login

server/routes/post-login.ts:198 and server/services/AuthService.ts:231–233

Apple only sends the user's email on the first sign-in ever. On every subsequent sign-in the email field is absent from Apple's response. The PostgreSQL row for the user already exists (from the first login), but ensureUserInPostgres is called again on each login and receives email = undefined. Because the function returns null when email is missing, it fails silently instead of looking up the existing row by Firebase UID. If the session was created in a fresh environment (new device, cleared cookies), the user effectively cannot be found and gets 404 USER_NOT_FOUND.

Bug 12 — Google OAuth: missing GOOGLE_WEB_CLIENT_SECRET causes a 500 error with no clear message

server/routes/mobile-auth.ts:11–12, 41

GOOGLE_WEB_CLIENT_SECRET has no fallback. If it is unset the client variable is null and the endpoint throws a generic 500 error when called. The environment variable MOBILE_LINK_SECRET (used as JWT secret in this route, line 13) is different from JWT_SECRET used everywhere else. If MOBILE_LINK_SECRET is unset, the JWT token is silently skipped at line 174 — the client may expect a token in the response and breaks without one.

Bug 14 — Social OAuth users have no wallet (except Google via mobile-auth.ts)

mobile-auth.ts auto-creates a wallet for Google users. Nothing in social-oauth.ts does the same for Instagram, TikTok, or Facebook. Bug 15 — OAuth intent lost after redirect: "Become Provider" via Google goes to /home

Bug 16 — Safari ITP loses the OAuth redirect marker

On cross-domain OAuth redirects (Firebase → petwash.co.il), Safari's Intelligent Tracking Prevention can clear localStorage between the redirect and the return. Both AuthProvider.tsx (on mount) and SignIn.tsx call getRedirectResult(). Firebase clears the result after the first read. Whichever reads second gets null. PetWash Marketplace — Full System Audit (April 2026)

This report covers Face ID/passkeys, admin access control, all API integrations, booking wiring, storage/backups, and active hacker entry points — building on the signup/provider analysis from the first session.

1 — FACE ID AND PASSKEYS (WebAuthn)

Architecture

There are two separate biometric systems that must not be confused:

System A — Passkey/WebAuthn login: Device Face ID or fingerprint used to sign in (via platform authenticator on iOS/Android).
System B — KYC face matching: Google Cloud Vision API comparing selfie to government ID for provider verification.
Critical Passkey Bugs

Bug P1 — Two conflicting WebAuthn implementations (CRITICAL) server/routes/webauthn.ts and server/routes.ts (lines 2760–2880) both define WebAuthn registration and login endpoints. They use different challenge storage backends (Firestore vs signed cookies). The client calls one; the other silently does nothing. One path may have security gaps that the other doesn't. There is no single source of truth.

Bug P2 — Challenge not stored server-side in /register/options (HIGH) server/routes/webauthn.ts:104 — The registration options endpoint generates a challenge and returns it to the client without storing it in the database. The verification step has no way to confirm the challenge was server-issued. An attacker who intercepts the challenge can replay it within the 5-minute window.

Bug P3 — /authenticate/verify has no auth middleware (HIGH) server/routes/webauthn.ts:256 — The authentication verification endpoint accepts any email and retrieves the Firebase user without requiring a prior session. This enables email enumeration: an attacker can probe any address and learn whether it has passkeys registered.

Bug P4 — Apple and Android attestation validation not implemented (HIGH) server/webauthn/config.ts:337–367 — Both validateAppleAttestation() and validateAndroidAttestation() are stubs that always return true. There is no certificate chain verification, no SafetyNet/Key Attestation check for Android, and no Apple App Attest check. Any device — including emulators and non-genuine hardware — can register passkeys.

Bug P5 — Credential storage split across three backends (MEDIUM) Passkey credentials are written to Firestore, to a JSONB column in the users table, and partially referenced in shared/schema.ts. There is no single authoritative store. A deleted Firestore document would leave an orphaned PostgreSQL record, causing login failure with no recovery path.

Bug P6 — Server reads VITE_FIREBASE_PROJECT_ID (client env var) for biometric bucket (MEDIUM) server/infra/biometricStorage.ts:14 — This server-side file uses the browser-prefixed env var. In environments where only server vars are set, the bucket name falls back to the hardcoded string "signinpetwash", pointing to the wrong GCS project.

All 14 are in server/routes/prestige-pass.ts. They use raw template literal string interpolation directly in SQL queries passed to pool.query():

4 — API INTEGRATIONS STATUS

Google Maps — API Key Exposed to Browser

server/routes.ts:659 reads process.env.VITE_GOOGLE_MAPS_API_KEY. The VITE_ prefix means this value is bundled into the client JavaScript and visible in any browser's developer tools or network inspector. Google Maps is a billable API. An exposed key can be used by anyone to run up charges. The fix is to use GOOGLE_MAPS_API_KEY (no VITE prefix) server-side only, and proxy map requests through the server rather than exposing the key to the browser.

Google Drive Backup — No Encryption

server/services/googleDriveBackupService.ts:176 — Backup files are uploaded as raw JSON.stringify() output. The backup contains invoices, digital signatures, biometric certificate records, provider applications, and security events. If the Google Drive account or service account is compromised, all this data is readable immediately. Backup data should be encrypted with AES-256 before upload.

Google Drive Backup — Silent Failure

server/services/googleDriveBackupService.ts:192–197 — Backup errors are caught and logged but no alert is sent (no email, no SMS, no Slack). Backups can fail silently for weeks with no visibility.

Google Sheets — 25+ Sheets Including Sensitive Data
