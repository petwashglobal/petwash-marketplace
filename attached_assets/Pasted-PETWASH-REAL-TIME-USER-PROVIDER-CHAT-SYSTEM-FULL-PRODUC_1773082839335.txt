PETWASH
REAL-TIME USER ↔ PROVIDER CHAT SYSTEM
FULL PRODUCT + UX + ENGINEERING SPEC
2026 MOBILE-FIRST EDITION

Goal
Build a complete real-time chat system for PetWash users and pet care providers across all relevant platforms, including:
- PetSitter
- Walk My Pet
- PetWash
- PetWash Academy where relevant
- future provider services

This must be a premium, ultra-modern, mobile-first communication system for iOS and Android with a luxury visual language:
- pure white background
- metallic accents
- very clean typography
- minimal clutter
- elegant cards
- fast and smooth transitions
- premium unread states
- polished interaction design

This is not a generic messaging tool.
It is a booking-bound, provider-safe, premium marketplace communication system.

==================================================
SECTION 1 — CORE CHAT MODEL
==================================================

The system must support:
1. customer ↔ provider real-time messaging
2. one conversation per booking / job / service engagement
3. optional support / admin visibility when needed
4. booking lifecycle aware chat states
5. mobile-first UX
6. read receipts, unread counts, notifications, archive
7. abuse reporting and moderation
8. luxury premium visual design

Golden rule:
No free messaging outside a valid service relationship unless explicitly allowed by product policy.

==================================================
SECTION 2 — CHAT TYPES
==================================================

Supported conversation types:

1. booking_chat
User and provider talk inside an active booking

2. support_chat
User and support/admin talk for help, dispute, billing, escalation

3. provider_admin_chat
Provider and internal staff communication when needed

Primary focus now:
booking_chat

==================================================
SECTION 3 — BOOKING CHAT LOGIC
==================================================

Conversation creation:
- exactly one conversation per booking
- created automatically when booking becomes confirmed
- not before confirmed state
- not available for anonymous browsing

Allowed states:
- draft = locked
- pending = locked
- confirmed = active
- in_progress = active
- completed = read_only
- cancelled = read_only
- expired = read_only
- disputed = read_only for user/provider, admin has access
- refunded = read_only
- no_show = read_only

Rules:
- only assigned customer and assigned provider may access the thread
- admin/support may have controlled read/moderation access
- no off-platform freeform messaging
- no duplicate conversations for same booking

SECTION 5 — REQUIRED API
==================================================

REST or RPC endpoints required:

GET /api/chat/:conversationId
GET /api/chat/:conversationId/messages
POST /api/chat/:conversationId/send
POST /api/chat/:conversationId/read
POST /api/chat/:conversationId/report
POST /api/chat/:conversationId/upload
POST /api/chat/:conversationId/archive
POST /api/chat/:bookingId/open-booking-chat

Admin:
GET /api/admin/chat/:conversationId
POST /api/admin/chat/messages/:messageId/moderate
POST /api/admin/chat/conversations/:conversationId/add-note

Support:
POST /api/support/chat/open
POST /api/support/chat/:conversationId/send

Requirements:
- strict auth on every route
- strict ownership validation
- no client-trust logic
- pagination
- cursor-based loading preferred
- idempotency for send
- rate limiting
- audit logging

SECTION 6 — REAL-TIME LAYER
==================================================

Use WebSocket / Socket.IO / similar real-time transport.

Required events:

Client → Server
- chat_subscribe
- chat_unsubscribe
- chat_typing_start
- chat_typing_stop
- chat_message_send
- chat_mark_read

Server → Client
- chat_message_new
- chat_message_updated
- chat_message_deleted_soft
- chat_read_receipt
- chat_unread_count
- chat_typing_presence
- chat_status_changed
- chat_system_event

Rules:
- server must validate ownership before room subscription
- unauthorized subscriptions must be rejected and logged
- events must be scoped to conversation room only
- never broadcast globally
- connection must be auth-bound
