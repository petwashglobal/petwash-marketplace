Proceed with implementation now, but build this as a production-grade 2026 booking-bound communication layer for iOS, Android, and web, not a generic chat.

CORE PRODUCT RULE
This must be a booking-scoped communication system only.
No free messaging.
No contact outside an active booking.
One booking = one conversation thread.

REQUIRED BUSINESS LOGIC

1. Conversation creation
- Create exactly one conversation per booking.
- Do not create a conversation before booking is actually accepted / confirmed.
- If booking is still draft, pending_payment, or pending_provider, chat must remain locked.
- If booking becomes confirmed or in_progress, chat becomes active automatically.
- If booking becomes completed, cancelled, expired, refunded, disputed, or no_show, chat becomes read-only automatically.
- Closed chats must remain visible as archive but not writable.

2. Allowed booking states
- LOCKED: draft, pending_payment, pending_provider, declined
- ACTIVE: confirmed, in_progress
- READ_ONLY: completed, cancelled, expired, disputed, refunded, no_show

3. Participants and authorization
- Only the assigned customer and assigned provider may read/write the conversation.
- Admin may read at any time and moderate when required.
- WebSocket subscribe must perform a database ownership check every time before joining the room.
- API fetch, send, read, and report routes must all independently enforce authorization server-side.
- Never trust client role or booking ID alone.

4. Data model
Use these two tables exactly, or equivalent if names differ:

bookingConversations
- id
- conversationId (BC-{uuid}, unique)
- bookingId (FK to bookings.id, unique per booking)
- platform
- customerId
- providerId
- chatStatus (locked | active | read_only | archived)
- closedReason (nullable: completed | cancelled | expired | disputed | refunded | no_show)
- customerUnread default 0
- providerUnread default 0
- lastMessageAt nullable
- lastMessagePreview nullable
- createdAt
- updatedAt
- closedAt nullable

bookingMessages
- id
- messageId (BM-{uuid}, unique)
- conversationId (FK to bookingConversations.conversationId)
- senderUid
- senderRole (customer | provider | system | admin)
- messageType (text | system_event | image)
- content
- systemEventType nullable
- isFlagged default false
- flaggedReason nullable
- moderatedBy nullable
- isDeleted default false
- deletedBy nullable
- readByCustomerAt nullable
- readByProviderAt nullable
- createdAt

5. System messages
Inject system messages automatically for:
- booking_confirmed
- provider_arriving
- in_progress
- completed
- cancelled
- expired
- dispute_opened
- refunded
- no_show
- chat_closed
These must be visually separate from user messages and immutable.

6. Messaging rules
- Text first-class support required.
- Optional image support only if implemented safely.
- No PDFs, executables, code files, zip files, or arbitrary attachments.
- Sanitize content for XSS and strip unsafe HTML.
- Max message length must be enforced server-side.
- Rate limit send endpoint per user and per conversation.
- Prevent duplicate sends by idempotency token or clientMessageId.
- Store timestamps in UTC.

7. Privacy and contact masking
- Do not expose customer or provider private email, phone, WhatsApp, Telegram, or direct off-platform details.
- Add detection for phone numbers, email addresses, URLs, and social handles.
- First version: flag suspicious messages for moderation review, and optionally soft-block depending on severity.
- Keep platform communication on-platform only unless business rules explicitly allow otherwise.

8. Read state and unread counts
- Maintain unread counters for customer and provider separately.
- Mark as read endpoint must update read timestamps and reset the relevant unread counter.
- Emit WebSocket events for new unread counts and read receipts.
- Message list must support pagination with cursor-based loading.

9. Notifications
- New message should trigger real-time socket event immediately.
- If recipient is offline, trigger fallback notification flow:
  a. in-app notification
  b. push notification if enabled
  c. email fallback if allowed by preferences
- Do not spam SMS for normal chat unless there is a critical escalation rule.

10. Admin and dispute support
- Admin must have read-only access to all booking chats.
- Admin moderation endpoint must support flagging, soft delete, hide from UI, and dispute review notes.
- Customer/provider must not be able to hard-delete the conversation history.
- Archived conversation history must remain available for support, disputes, escrow investigation, and legal review.
