אם אתם חייבים לשמור על תמונה “לא חתוכה”, אז במקום cover:
	•	תעשו object-fit: contain אבל אז תקטינו את הקונטיינר (aspect-ratio אחר) ותורידו padding, אחרת תמיד יהיה שטח מת.

⸻

3.2 RTL ויישור טקסט

בדפי עברית חובה:
	•	direction: rtl
	•	text-align: right
	•	ליישר כפתורים ו־icons שלא יברחו

לרוב יש “חצי RTL” וזה יוצר רווחים מוזרים.

⸻

3.3 טפסים: Become Provider חייב להיות “bulletproof”

חובה שיהיה:
	•	שלבים ברורים (Step 1, Step 2, Step 3)
	•	שמירה אוטומטית (draft)
	•	הודעת הצלחה ברורה + מה השלב הבא
	•	טיפול בשגיאה עם הודעה ספציפית, לא “משהו השתבש”

⸻

4) Back End: למה Become Provider נשבר ואיך מתקנים

4.1 חוזה נתונים אחיד (מינימום הכרחי)

Collections מומלצות
	•	users/{uid}
	•	providerApplications/{uid}
	•	providers/{uid}
	•	auditLogs/{id}

זרימת Provider נכונה
	1.	user ממלא בקשה
	2.	נוצרת providerApplications/{uid} עם status = pending
	3.	Cloud Function מאמתת ושומרת audit log
	4.	Admin מאשר
	5.	נוצרת רשומת providers/{uid} + עדכון users/{uid}.role = provider
	6.	כל המערכות קוראות את role רק מהשרת/DB

⸻

4.2 הטעות הכי נפוצה: Role רק בצד לקוח

אם ה־UI מחליף “מצב” ל־provider אבל DB לא עודכן, המשתמש יתקע אחרי רענון.

כלל ברזל:
	•	Role הוא server-side truth
	•	UI רק מציג

⸻

4.3 Firestore Rules שמפילים רישום

אם כללי אבטחה לא מאפשרים כתיבה ל־providerApplications, הטופס “נראה כאילו נשלח” אבל בפועל נכשל.

חובה:
	•	לוג שגיאות מסודר
	•	Sentry או לפחות Cloud Logging
	•	להחזיר הודעת שגיאה אמיתית למשתמש

⸻

4.4 Audit log לכל פעולה קריטית

כל דבר שקשור:

	•	יצירת Gift
	•	סטטוס תשלום

צריך Audit Log עם:
	•	מי עשה
	•	מתי
	•	מה השתנה
	•	ערך ישן וחדש

בלי זה אין שליטה פיננסית.
