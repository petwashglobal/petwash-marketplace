TOP 50 LIVE ISSUES RANKED BY PRODUCTION RISK

CRITICAL (Exploitable Now)

#1 — Demo Payment Mode Falls Back to Fake Payments on Missing API Key

File: server/services/NayaxSparkService.ts:40
Code: const DEMO_MODE = process.env.NAYAX_DEMO_MODE === 'true' && !NAYAX_API_KEY;
This flag silently makes ALL payments simulated. If NAYAX_API_KEY is not set in the env, any user can book and pay without a real charge. No error is thrown — service succeeds.
Affected: All paying users, finance, operations
Fix: if (!NAYAX_API_KEY) throw new Error('NAYAX_API_KEY is required in production') — never fall back to demo
#2 — Auto-Approval of Providers Without Human Review

File: server/routes/provider-onboarding.ts:909-918
Code: If faceScore >= 85 && livenessPass && flags.length === 0 → provider is instantly activated, reviewedBy = 'system-kyc2026'
Any attacker with a decent photo and a static deepfake can self-approve as a provider, getting access to customer bookings and payout flows, with no human ever in the loop
Affected: Customers who get unvetted providers, platform safety, compliance
Fix: ALL approvals must route through admin queue. Remove auto-approval entirely
#3 — Background Check Status Is SET, Not Validated

File: server/routes/provider-onboarding.ts:916-917
Code: backgroundCheckStatus = 'passed' is written by the system as a side effect of passing face match. Police check service is optional and only invoked for sensitive categories. Criminal background check is stored but not run.
A dangerous actor can register, pass KYC selfie, and have backgroundCheckStatus = 'passed' without any criminal check running
Affected: All customers booked with providers, platform liability
Fix: Make policeCheckId a hard prerequisite before providerStatus can reach active
#4 — Hardcoded Super Admin UID in 7+ Route Files

File: server/routes/disputes.ts:18, server/routes/provider-trust.ts:32, lines 435, 481, 541, 566, 617, 683, 704
Code: const SUPER_ADMIN_UID = 'vdiboz7IrUQEm2RbdO7VZLkBu552';
UID is a string in source code. If it leaks (GitHub exposure, ex-employee), attacker has permanent admin access. Cannot be rotated without code deploy.
Affected: All admin functions, disputes, provider trust
Fix: Load from SUPER_ADMIN_UID env var at startup; rotate freely
#5 — Hardcoded Personal Email (nirhadad1@gmail.com) Used for Authorization in 9+ Files

Files: server/middleware/rbac.ts:17, server/routes/admin.ts:952, server/routes/push-notifications.ts:95, server/routes/wallet.ts:842, server/routes/admin-loyalty.ts:38-40, server/routes/pets.ts:180, server/routes/expenses.ts:141, 236, 293, 359, server/routes/prestige-pass.ts:2231
A personal Gmail is used as the authorization gate for wallets, admin, push notifications, and expenses. If this Gmail is compromised, entire platform admin is compromised.
Fix: Remove ALL hardcoded emails. Use SUPER_ADMIN_EMAILS env var exclusively
#6 — Booking Completion Has No Ownership Check

File: server/routes/bookings.ts:588-633
Code: await db.collection("bookings").doc(bookingId).update({ status: "completed" }) — no WHERE clause against booking.customerId or booking.providerId
Any authenticated user can mark any booking as completed by knowing its ID, triggering escrow release to the wrong party
Affected: All booking customers, providers, finance
Fix: if (booking.providerId !== req.user.uid && booking.customerId !== req.user.uid) return 403
#7 — reCAPTCHA Is Deliberately Fail-Open on Phone OTP

File: server/routes/publicAuthRoutes.ts:1300+
Code: securitySource = 'captcha-failed-proceed' — SMS send proceeds even if captcha fails
Attacker can send unlimited OTP SMS to any phone by bypassing reCAPTCHA, creating cost and SMS bombing risk
Fix: If captcha score < 0.3, block SMS entirely. Log it as abuse attempt.
#8 — amountIls Trusted from Client in Pass Redemption

File: server/routes/pass-redeem.ts:58, 179-186
Code: z.number().positive().max(10_000) — client sends amount. Whitelist VALID_WASH_PRICES_ILS exists but is not bound to machine or service type.
User can redeem 200 ILS credit for a 45 ILS wash by calling the endpoint directly
Fix: Amount must be derived from the station/service lookup server-side, not from the request body
#9 — Free-Text Status Columns in Database (No DB-Level Enum)

File: shared/schema.ts:106 and throughout
Code: role: varchar("role").default("customer") — string, no CHECK constraint
SQL injection or direct DB access can set role = 'admin' on any user row. State machine is enforced only at application layer.
Fix: Convert role, booking_status, provider_status, voucher_status to PostgreSQL ENUM types
#10 — Multiple Provider Onboarding Paths With Inconsistent KYC (7 Paths)

Files: provider-onboarding.ts, provider-applications.ts, sitter-suite.ts, walk-my-pet.ts, octopus-engine.ts, globalForms.ts, admin manual approval
Each path has different validation, some with no KYC at all. Attacker finds weakest path.
Affected: Platform safety, all customers, compliance
Fix: Single canonical onboarding route; all others return 410
#11 — Wallet Race Condition: Two-Phase Upsert Loses Concurrent Credits

File: server/routes/walk-my-pet.ts (wallet refund logic)
Code: INSERT ... ON CONFLICT DO NOTHING followed by separate UPDATE wallet_accounts SET cash_wallet_balance_cents = cash_wallet_balance_cents + $1
Two simultaneous refunds for the same user can run the UPDATE twice or lose one credit
Fix: Use INSERT ... ON CONFLICT DO UPDATE SET balance = balance + EXCLUDED.amount in a single atomic statement inside a transaction
#12 — Escrow Release Without Buyer Confirmation

File: server/routes/bookings.ts:602-609
Provider can call completion endpoint → funds released from escrow with no customer confirmation required
Fix: Require dual-party confirmation (customer + provider) before escrow release, or implement auto-release only after dispute window expires
#13 — Dual Wallet Systems Without Reconciliation (wallet_accounts vs petwash_pass_accounts)

File: shared/schema.ts:11321, 11331-11338
Two balance systems exist; code comment says "balance authority lives in wallet_accounts" but redemption on pass account doesn't update wallet_accounts
Double-spend attack: redeem from pass account, then simultaneously from wallet_accounts
Fix: Single source of truth. One table, one balance.
#14 — Wallet Ledger Is NOT Immutable at Database Level

File: shared/schema.ts:11355-11380
Code says "Append-only, no updates or deletes" but there is no database-level RULE or trigger preventing DELETE/UPDATE on wallet_ledger_entries
Compromised admin or bug can retroactively delete financial history
Fix: Add PostgreSQL rule: CREATE RULE no_delete_ledger AS ON DELETE TO wallet_ledger_entries DO INSTEAD NOTHING
#15 — QR Blockchain Hash Not Verified at Redemption

File: server/routes/gift-cards.ts:61-75
SHA256 hash of voucher is computed but never validated server-side during redemption. Hash is ceremonial.
Attacker can forge QR showing inflated amount; server does not verify hash
Fix: Store hash in DB at issue time; verify at redemption time
#16 — Biometric Documents Stored Unencrypted in GCS

File: server/routes/provider-onboarding.ts:735-740
Selfies and government IDs stored at selfies/${userId}/${timestamp}.jpg without encryption
DocumentEncryption class (AES-256-GCM) exists but is NOT applied to biometric docs
Fix: Apply DocumentEncryption to all uploaded biometric files before GCS write
#17 — VITE_ Frontend Env Vars Used Server-Side

File: server/routes.ts:40-50, server/routes/provider-onboarding.ts:1296, 1304
Code: process.env.VITE_FIREBASE_PROJECT_ID used to construct GCS bucket URL on server
VITE_ vars are compiled into the frontend bundle. If a CI/CD .env is shared, Firebase project keys are doubly exposed
Fix: Server uses FIREBASE_PROJECT_ID only. Never reference VITE_* in backend
#18 — Timing Attack on Admin Secret in 9+ Routes

Files: server/routes/teams.ts:38, station-dashboard.ts:47, case-reports.ts:24, financial-approvals.ts:28, booking-trace.ts:50, case-queue.ts:85, case-actions.ts:49, station-settlements.ts:28, server/middleware/stationAuth.ts:35
Code: req.headers['x-admin-secret'] === ADMIN_SEC — plain ===, not timingSafeEqual
The correct pattern already exists in server/middleware/adminAuth.ts but is inconsistently applied
Fix: Replace all === secret comparisons with crypto.timingSafeEqual(Buffer.from(a), Buffer.from(b))
#19 — Role Parameter Trusted from Query String

Files: server/routes/sitter-suite.ts:1124, booking-requests.ts, loyalty.ts, marketplace-bookings.ts
Code: const role = req.query.role as 'owner' | 'sitter'
Client can send ?role=provider to access provider-only views
Fix: Role must be derived from Firebase custom claims, never from request
#20 — Invoice Routes (ITA) Lack Auth Middleware

File: server/routes/ita-api.ts:62, 96, 112, 128, 164
Invoice create/submit/status for Israeli Tax Authority have no visible requireAuth
Unauthenticated users can create/submit tax invoices for other users' commissions
Fix: Add requireAuth to all ITA routes immediately
#21 — Unauthenticated Provider Browse Exposes PII

File: server/routes/provider-trust.ts:160
Code: router.get('/providers/browse', async (req: Request, res: Response) => { — no auth check
Returns first_name, last_name, background_check_status, has_fenced_yard, rating data to any unauthenticated request
Fix: Add requireAuth middleware
#22 — Deprecated Octopus Engine Still Processing Bookings

File: server/routes/octopus-engine.ts:1-14
Marked [DEPRECATED — V1 API] in comment at top, but POST /api/octopus/v1/bookings logs a warning and continues processing. 1,687 lines of active legacy code.
Old ledger/wallet tables may have SQL injection vulnerabilities not present in newer code
Fix: Return 410 Gone from all octopus routes
#23 — No Idempotency on Nayax Webhook / New Booking Flow

File: server/routes/nayax-payments.ts
V1 octopus bookings have idempotency; new booking-requests flow does NOT. No processed_webhooks table.
Webhook replay = double wallet credit
Fix: Create processed_webhook_events(event_id TEXT PRIMARY KEY, processed_at TIMESTAMP) and check before processing
#24 — Contractor Invoice IDOR

File: server/routes/contractor-invoices.ts:14, 66
GET /:commissionId/generate and GET /:commissionId/preview take commissionId from URL without verifying the calling user owns that commission
Attacker can download any contractor's invoice by guessing sequential IDs
Fix: Add WHERE user_id = $currentUser to query
#25 — National Insurance / Tax ID Stored as Plaintext

File: server/routes/contractor-onboarding.ts:190, 194
taxId, nationalInsuranceNumber stored as unencrypted DB columns
If DB breached, Israeli NI numbers and tax IDs are exposed. Non-compliant with Israeli Privacy Law 2025.
Fix: Encrypt with DocumentEncryption before storage
#26 — Google Drive Backups Unencrypted, No PII Masking

File: server/services/googleDriveBackupService.ts
Full database JSON uploaded to Drive with no encryption and no PII field masking
Compromise of Drive account = entire customer database exposed
Fix: Encrypt backup files with AES-256 before upload. Mask PII fields.
#27 — Liveness Detection Is Heuristic, Not Certified

File: server/services/KYC2026/KYCMemoryProcessor.ts
Uses Google Vision landmark ratios + blur + pose heuristics. Code comment: "For certified passive liveness, integrate FaceTec or iProov."
Deepfake videos or printed photos with face annotations will pass
Fix: Integrate FaceTec or iProov before accepting any more provider KYCs
#28 — Provider Stats Endpoint Likely Unauthenticated

File: server/routes/control-panel.ts:261
Code: router.get("/providers/stats", async (req, res) => { — no visible auth
Exposes pending/approved application counts to public, enables enumeration
Fix: Add auth + admin role check
#29 — Gift Card Redeemed Flag Not Atomic

File: server/routes/gift-cards.ts:150+
No atomic transaction wrapping the check-then-set of redeemed flag. SELECT then UPDATE pattern.
Concurrent requests can redeem the same gift card twice
Fix: UPDATE vouchers SET redeemed = true, used_at = now() WHERE id = $1 AND redeemed = false RETURNING * — reject if 0 rows affected
#30 — Negative Balance Risk in Loyalty Points (Non-Atomic Check+Debit)

File: server/services/K9000RedemptionService.ts
SELECT balance, check ≥ threshold, then UPDATE — separate operations. Race condition allows two concurrent debits to pass check.
Fix: UPDATE loyalty SET points = points - $1 WHERE user_id = $2 AND points >= $1 RETURNING *
