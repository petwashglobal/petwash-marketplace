FINDING 1 — GENERIC TRANSITION ENDPOINT HAS NO BOOKING OWNERSHIP CHECK

Category: Missing Permission Check | Severity: CRITICAL

File: server/routes/marketplace-bookings.ts:548–577

TypeScript
router.post('/:bookingId/transition', async (req, res) => {
  const userId = req.user?.uid || req.firebaseUser?.uid;
  if (!userId) return res.status(401).json({ error: 'Authentication required' });

  const { newStatus, role = 'customer', reason } = req.body;  // role from body — not verified

Any authenticated user who knows a bookingId can call this endpoint and drive the booking to any valid next state. There is no check that userId is the customer or provider on the booking. The role field is accepted verbatim from the request body — a customer can send role: "admin". BookingLifecycleService.transitionStatus() validates the state machine transitions but never verifies the actor's identity against the booking record.

FINDING 13 — INVOICE NUMBER IS NOT SEQUENTIAL (COMPLIANCE RISK)

DATABASE

What is solid

The schema is comprehensive and well-structured for the complexity it covers. Drizzle ORM with parameterised queries eliminates SQL injection across the board. Indexed joins on the most-queried booking table columns exist. Atomic DB transactions are used in the marketplace checkout flow (quote → slot lock → escrow → booking) which prevents double-booking. The wallet and escrow idempotency key pattern is correctly designed.

What is broken or missing

1 — Redundant and conflicting role storage on the users table

users.role (single varchar), users.roles (JSONB array), and users.permissions (JSONB array) all exist simultaneously with no synchronisation mechanism. The application can read from any of the three. There is also a userRoles join table that is maintained in parallel. When a user's role changes, if only one of the four places is updated, the system will produce inconsistent access decisions. This is the most dangerous structural data bug in the entire schema.

Files: shared/schema.ts (lines 35–154), server/services/rbac.ts

2 — 40+ status and state columns are free-text varchar instead of enums

bookings.status, bookingRequests.financeState, users.activationStatus, users.journeyState, and dozens more accept any string. PostgreSQL ENUM constraints would guarantee only valid transitions can be written. As it stands, a code bug, migration error, or direct DB write can put a record in an impossible state silently.

Files: shared/schema.ts throughout

3 — Three separate escrow systems coexist

EscrowService (Firestore collection escrow_payments) — used by Sitter Suite, Walk My Pet, booking-requests, bookings.ts
escrowHoldings (PostgreSQL table) — used exclusively by marketplace-bookings.ts
EscrowStateMachine (PostgreSQL table via BillingEngine) — used by BillingEngine for financial settlements
These three systems are not synchronised with each other. A booking created through marketplace-bookings.ts writes to escrowHoldings. A booking created through booking-requests.ts writes to Firestore. The dispute flow in disputes.ts does not interact with any escrow system at all when resolving — it only updates a status column. This means marking a dispute as "resolved" does not automatically trigger a refund or escrow release. An admin must manually take a separate action.

The gap is in the consumer side — marketplace-bookings.ts does not verify that a provider still owns the slot at checkout time by cross-referencing availabilitySlots.providerId against the quote's providerId.
