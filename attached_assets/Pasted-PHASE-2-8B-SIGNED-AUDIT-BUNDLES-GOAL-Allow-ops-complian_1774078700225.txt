PHASE 2.8B — SIGNED AUDIT BUNDLES

GOAL
Allow ops/compliance to download one tamper-evident JSON bundle for:
1. a booking
2. a user wallet

The bundle must include the raw trail plus a deterministic SHA-256 signature.

==================================================
BACKEND
==================================================

FILE
- server/routes/prestige-pass.ts

NEW ENDPOINT
GET /api/prestige-pass/admin/wallet/audit-bundle/:subjectType/:subjectId

PARAMS
- subjectType = booking | user
- subjectId = bookingId or userId

AUTH
- same admin guard as the other finance endpoints

RESPONSE HEADERS
- Content-Type: application/json
- Content-Disposition: attachment; filename="audit-bundle-<type>-<id>-<ts>.json"

==================================================
BUNDLE SHAPE
==================================================

{
  "bundleVersion": "1",
  "subjectType": "booking",
  "subjectId": "BK-123",
  "generatedAt": "2026-03-21T18:45:00.000Z",
  "generatedBy": "adminUid",
  "ledgerEntries": [...],
  "bookingSnapshot": {...},
  "actionHistoryRows": [...],
  "signature": "sha256:<hex>"
}

==================================================
BOOKING BUNDLE CONTENT
==================================================

ledgerEntries
- all wallet_ledger_entries linked by booking_id = subjectId
- ordered ASC by created_at, then id

bookingSnapshot
- if bookingId exists in booking_requests:
  - include full marketplace finance snapshot
- else if exists in trainer_bookings:
  - include full academy finance snapshot
- normalize:
  {
    bookingId,
    sourceTable: "booking_requests" | "trainer_bookings",
    userId,
    providerId,
    status,
    financeState,
    walletHoldCents,
    walletDebitedCents,
    walletRefundedCents,
    walletHoldKey,
    walletDebitKey,
    walletReleaseKey,
    walletRefundKey,
    createdAt,
    updatedAt
  }

actionHistoryRows
- reuse the action-history query helper
- filter by bookingId = subjectId
- ordered ASC by createdAt

==================================================
USER BUNDLE CONTENT
==================================================

ledgerEntries
- all wallet_ledger_entries for user_id = subjectId
- ordered ASC by created_at, then id
- cap at 2000 rows for first pass
- if capped, include metadata note in bookingSnapshot or top-level bundle note

bookingSnapshot
- actually user snapshot here:
  {
    userId,
    walletAccount: {
      cashWalletBalanceCents,
      egiftBalanceCents,
      promoBalanceCents,
      referralBalanceCents,
      loyaltyPointsBalance,
      pendingBalanceCents,
      lifetimeEarnedCents,
      lifetimeRedeemedCents,
      updatedAt
    },
    bookingFinanceSummary: {
      holdActiveCount,
      debitedCount,
      refundedCount,
      releasedCount,
      totalHeldCents,
      totalDebitedCents,
      totalRefundedCents
    }
  }

actionHistoryRows
- reuse action-history helper
- filter by userId = subjectId

==================================================
SIGNATURE
==================================================

Use Node crypto:
- createHash('sha256')

Signature input:
canonical JSON of:
{
  ledgerEntries,
  bookingSnapshot,
  actionHistoryRows,
  generatedAt
}

Critical:
- deterministic key sort
- no whitespace variance
- stable array ordering before hashing

Recommended helper:
stableStringify(value)

Rules:
- sort object keys alphabetically
- preserve array order
- stringify primitives normally

Then:
signature = "sha256:" + createHash("sha256").update(stableJson).digest("hex")

==================================================
ERROR HANDLING
==================================================

404
- subject not found in both booking tables for booking bundle
- wallet/user not found for user bundle

400
- invalid subjectType

500
- unexpected query/signature failure

==================================================
ACCEPTANCE CHECKLIST
==================================================

1. Booking bundle
- download succeeds
- includes bookingSnapshot
- includes linked ledger entries
- includes action history
- signature field present

2. User bundle
- download succeeds
- includes wallet balances + finance summary
- includes ledger entries
- includes user action history
- signature field present

3. Determinism
- same booking downloaded twice with unchanged data
- signature identical

4. Mutation sensitivity
- perform one new admin action
- download again
- signature changes

5. Unknown subject
- returns 404, not 500
