PETWASH - PLATFORM INTELLIGENCE REPORT  
Brands, Platforms, Services, and Operations

==================================================
1. WHAT PETWASH REALLY IS
==================================================

PetWash is not a feature product.  
It is a multi-sided service ecosystem with:

- physical infrastructure (kiosks)
- digital marketplace (services)
- financial layer (wallet, credits, payments)
- identity layer (users, providers)
- loyalty system (membership, rewards)
- operations system (support, review, audit)
- communication system (notifications, messaging)

If you build it like a simple app, it will collapse.  
You must build it like a controlled operating system.

==================================================
2. CORE BUSINESS DIMENSIONS
==================================================

Every action in the system belongs to 4 dimensions:

1. Identity
   Who is acting?
   - public member
   - provider
   - support
   - admin
   - system

2. Platform
   Where is the action happening?
   - kiosk (physical)
   - mobile app
   - web app
   - admin dashboard
   - provider dashboard

3. Service
   What is being consumed?
   - dog wash
   - pet sitting
   - dog walking
   - training
   - marketplace products
   - loyalty benefits

4. Financial Layer
   How is it paid?
   - wallet
   - e-gift
   - package credit
   - coupon
   - external processor

If a feature does not clearly define all four, it is incomplete.

==================================================
3. BRAND ARCHITECTURE
==================================================

PetWash is one brand externally, but internally it has multiple products:

A. PetWash Kiosk
- self-service dog washing stations
- instant use, fast transaction
- QR / NFC / app start
- real-time hardware integration

B. PetWash Club (Loyalty)
- membership system
- rewards, benefits, discounts
- wallet-centric experience
- retention engine

C. PetWash Services Marketplace
- sitters
- walkers
- trainers
- providers
- booking + scheduling system

D. PetWash Wallet
- stored value system
- credits, refunds, promotions
- must be 100% accurate and auditable

E. PetWash Admin & Operations
- provider onboarding
- review queues
- support actions
- campaign management

Each of these must feel unified to the user, but internally they are different systems sharing one core brain.

==================================================
4. PLATFORM LAYERS
==================================================

You are building 5 layers:

1. Experience Layer
- mobile UI
- web UI
- kiosk UI

2. Application Layer
- booking logic
- coupon logic
- wallet logic
- provider logic

3. Domain Layer
- rules
- state machines
- eligibility
- permissions

4. Data Layer
- database
- ledger
- audit
- storage

5. Integration Layer
- payment processors
- SMS/email providers
- identity providers (Apple, Google)
- external verification APIs

If logic leaks between layers, system becomes unstable.

==================================================
5. SERVICES MODEL
==================================================

Each service has a different behavior model:

Kiosk wash
- immediate
- prepaid or wallet-funded
- no scheduling
- hardware-triggered
- must be idempotent

Sitter / walker / trainer
- scheduled
- multi-day or time-based
- provider assignment
- cancellation rules
- partial refunds possible

Marketplace products
- cart-based
- delivery or pickup
- inventory aware

Loyalty benefits
- passive or triggered
- discount or credit
- eligibility-based

Do not try to unify all services under one naive “order” model.  
They share concepts, but not behavior.

==================================================
6. OPERATIONS MODEL
==================================================

Operations must run like a control tower.

Key queues:

- provider onboarding queue
- pending review queue
- resubmission queue
- support tickets
- failed transactions
- refund requests
- fraud alerts

Each item must have:
- status
- owner
- history
- next action

Support must never guess.

==================================================
7. FINANCIAL TRUTH
==================================================

The wallet is the heart of trust.

Rules:

- balance must always be correct
- every change must be logged
- reservation must exist before usage
- release must happen on failure
- refunds must restore correctly
- no silent adjustments

Every transaction must be explainable line by line.

If finance is unclear, users lose trust immediately.

==================================================
8. COUPON AND PROMOTION INTELLIGENCE
==================================================

Coupons are not discounts.  
They are controlled liabilities.

Every coupon must answer:

- who can use it?
- where can it be used?
- when can it be used?
- how many times?
- can it stack?
- what happens on cancel?

Campaign vs issued coupon must always be separated.

Bad coupon logic causes:
- financial leakage
- abuse
- support overload
- inconsistent UX

==================================================
9. IDENTITY AND ROLES
==================================================

One person can have multiple roles:
- loyalty member
- provider
- admin (rare)
- support (internal)

But roles must be activated, not assumed.

Never mix:
- public flow with provider flow
- provider privileges before approval
- admin access without audit

Identity must always answer:
- who is this user?
- what roles are active?
- what can they do right now?

==================================================
10. STATE MACHINES ARE NON-NEGOTIABLE
==================================================

Every major object must have strict states:

User:
- new → verified → active → suspended

Provider:
- submitted → processing → review → approved/rejected

Booking:
- draft → reserved → confirmed → completed → cancelled/refunded

Coupon:
- draft → active → paused → archived

Wallet transaction:
- pending → reserved → committed → reversed

Without strict transitions, bugs multiply.

==================================================
11. FAILURE-FIRST DESIGN
==================================================

Assume everything can fail:

- payment processor timeout
- OTP delay
- provider does not respond
- user cancels late
- kiosk fails to start
- duplicate callbacks
- network retries

System must:
- not lose state
- not double-charge
- not double-redeem
- not corrupt wallet
- allow recovery

Reliability is more important than speed.

==================================================
12. COMMUNICATION SYSTEM
==================================================

Messaging is operational infrastructure.

Types:
- transactional (booking, payment)
- operational (review, resubmission)
- marketing (campaigns)

Rules:
- transactional can bypass marketing consent
- marketing must respect consent
- all messages must be traceable

Every important event should generate:
- notification
- log
- optional message thread

==================================================
13. DATA IS THE SOURCE OF TRUTH
==================================================

Never rely on:
- frontend state
- temporary variables
- external tools as primary storage

Always rely on:
- database
- ledger
- audit tables

If something is not stored, it does not exist.

==================================================
14. GROWTH ENGINE
==================================================

Growth depends on:

- frictionless signup
- immediate value (wallet, benefits)
- clear UX
- trust in payments
- reliable services

The weakest link is usually:
- onboarding
- payment confusion
- unclear status

Fix those first.

==================================================
15. WHAT MAKES IT A REAL SYSTEM
==================================================

A real PetWash system is one where:

- a new user signs up in seconds
- a provider can onboard without confusion
- a booking never double-charges
- a coupon never breaks finance
- a wallet never lies
- support always knows what happened
- management sees real data
- failures do not corrupt state

If any of these fail, the system is not ready.

==================================================
16. FINAL PRINCIPLE
==================================================

Do not build features.

Build:
- flows
- states
- guarantees
- trust

Features can be added later.

Trust cannot.
